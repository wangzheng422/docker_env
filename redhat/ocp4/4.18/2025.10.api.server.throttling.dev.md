as we can see, `workload-low` has 100 concurrency, which may be too high for etcd, so we create a dedicate `PriorityLevelConfiguration` and `FlowSchema` for our workload, which is `dagster`

```yaml
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: PriorityLevelConfiguration
metadata:
  name: dagster-limit  # 1. 创建一个新的“安检通道”，名为dagster-limit
spec:
  type: Limited
  limited:
    # 2. 为这个通道设置一个非常低的并发份额。
    #    (global-default是20，workload-low是100，我们给它一个更低的值)
    assuredConcurrencyShares: 5 
    limitResponse:
      queuing:
        queueLimit: 10 # 最多只排10个请求
        handSize: 4    # 每次只处理4个
      type: Queue
---
apiVersion: flowcontrol.apiserver.k8s.io/v1
kind: FlowSchema
metadata:
  name: dagster-jobs-flow
spec:
  # 3. 设置一个高匹配优先级(数字越小越优先)
  #    我们设为8000，这会比 service-accounts (9000) 更早被匹配到
  matchingPriority: 8000
  
  # 4. 指向我们上面创建的那个严格的“限速通道”
  priorityLevelConfiguration:
    name: dagster-limit
    
  # 5. 定义匹配规则
  rules:
  - resourceRules:
    - apiGroups: ["*"]
      resources: ["*"]
      verbs: ["*"]
      # 替换 "dagster-ns" 为您Dagster Job所在的命名空间
      namespaces: ["dagster-ns"] 
    subjects:
    # 替换 "dagster-sa" 为您的Job使用的服务账户
    - kind: ServiceAccount
      name: dagster-sa
      namespace: dagster-ns
```
