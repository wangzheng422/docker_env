# OVN egressip limitation workaround

## Background

customer install a ocp 4.18 on 3rd part osp, using baremetal install method. and the osp has limitation of 10 elastic ip on each node. but the security require each namespace has a dedicate egress ip, and there are 40+ namespaces. and the elastic ip pools contains different subnets, and worker node has different associated relationship with elastic ip pools subnets. current ovn does not support node selector for egressip. and only single pool of egressip is supported. so we need to implement a workaround to support this requirement.

the basic idea is to use a gateway pod for each namespace to provide egress ip for the namespace. use ovn config to route the traffic to the gateway pod for the namespace pod. and use a tool pod to monitor the gateway pod's ip, and change ovn config's next hop ip when the gateway pod restart.

in this demo, we have ocp 4.18 installed, 3 master, 2 worker, worker node ip is 192.168.99.26, 192.168.99.27, I have a big rhel 9 machine, and I create the 5 node with kvm, so there should no mac restrict on the network.

## Workaround

```bash

oc create ns ns-egress-infra

  kind: ClusterRole

spec:

      "cniVersion": "0.3.1",
      "type": "macvlan",

      "mode": "bridge",

        "type": "static"

oc create sa gateway-sa -n ns-egress-infra

# 为该 SA 授予 privileged SCC

kind: Deployment
metadata:
  name: ns-blue-gateway
  namespace: ns-egress-infra
spec:
  replicas: 1 
  selector:
    matchLabels:
      app: ns-blue-gateway
  template:
    metadata:
      labels:
        app: ns-blue-gateway
      annotations:
        k8s.v1.cni.cncf.io/networks: '[
          {
            "name": "ns-blue-external-macvlan", 
            "interface": "macvlan0",
            "ips": ["192.168.99.2/24"]
          }
        ]'
    spec:
      serviceAccountName: gateway-sa
      nodeSelector:
        egress-node: ns-blue-group
      containers:
      - name: gateway
        image: registry.redhat.io/openshift4/ose-egress-router:latest
        command: ["/bin/sh", "-c"]

          sysctl -w net.ipv4.ip_forward=1
          sysctl -w net.ipv4.conf.all.rp_filter=0
          sysctl -w net.ipv4.conf.default.rp_filter=0
          sysctl -w net.ipv4.conf.eth0.rp_filter=0
          sysctl -w net.ipv4.conf.macvlan0.rp_filter=0

          sysctl -w net.ipv4.conf.eth0.accept_local=1
          sysctl -w net.ipv4.conf.all.accept_local=1

          iptables -P FORWARD ACCEPT
          
          # 1. 保存 OVN 网络原本的网关
          OVN_GW=$(ip route show default | awk '/default/ {print $3}')

          ip route add 10.0.0.0/8 via $OVN_GW dev eth0
          ip route add 172.16.0.0/12 via $OVN_GW dev eth0
          
          # 3. 确保 macvlan0 接口已启动
          ip link set macvlan0 up
          
          # 4. 切换默认路由指向物理网关
          ip route del default
          ip route add default via 192.168.99.1 dev macvlan0
          
          # 获取gateway pod的OVN IP
          GW_OVN_IP=$(ip -4 addr show eth0 | grep -oP '(?<=inet\s)\d+(\.\d+){3}')
          
          # 5. 关键修改:添加策略路由来处理来自其他pod的流量
          # 为来自OVN网络的流量创建单独的路由表
          # ip rule add from 10.132.0.0/14 table 100 priority 100
          # ip route add default via 192.168.99.1 dev macvlan0 table 100
          # ip route add 10.0.0.0/8 via $OVN_GW dev eth0 table 100
          # ip route add 172.16.0.0/12 via $OVN_GW dev eth0 table 100
          # 经过测试，上面的路由不work
          ip route del default
          ip route add default via 192.168.99.1 dev macvlan0
          
          # 6. SNAT规则
          # 对从eth0出去的流量做SNAT (内网流量)
          iptables -t nat -A POSTROUTING -o eth0 -j SNAT --to-source $GW_OVN_IP
          
          # 对从macvlan0出去的流量做SNAT (外网流量)
          iptables -t nat -A POSTROUTING -o macvlan0 -j SNAT --to-source 192.168.99.2
          
          echo "Gateway started! Egress IP: 192.168.99.2, Physical GW: 192.168.99.1, OVN IP: $GW_OVN_IP";
          ip route show
          iptables -t nat -L -n -v
          
          # 防止容器退出
          sleep infinity;
        securityContext:
          privileged: true
EOF


```

## OVN Network Configuration Patches

### Why Patching is Required

OpenShift OVN 默认的安全机制会阻止我们的 gateway pod 方案正常工作。我们需要绕过这些安全检查以实现自定义的出口路由。

**核心问题:**

1. **Port Security 限制**
   - OVN 默认启用 Port Security,只允许 pod 发送源 IP 为自己的流量
   - Gateway pod 需要转发来自其他 pod 的流量(源 IP 不是 gateway pod 自己)
   - 如果不清除 Port Security,gateway pod 转发的流量会被 OVN 丢弃

2. **Stateful ACL 的源 IP 检查**
   - OVN 默认使用 stateful ACL 进行连接跟踪
   - 当 business pod 通过 gateway 访问外部 IP(如 8.8.8.8)时,返回流量的源 IP 是 8.8.8.8
   - Stateful ACL 会检查返回流量的源 IP,发现不匹配而丢弃
   - 这导致 DNS 查询、HTTPS 请求等都会失败

### What We Patch

我们对 OVN 进行了以下修改(这些逻辑已集成到 [controller.py](files/ovn.egressip/controller.py) 中):

**1. Gateway Pod 配置**
```
- 清除 Port Security (allow-stateless)
  → 允许转发源 IP 不是自己的流量
  
- 添加 Stateless ACL (优先级 31821)
  → from-lport: 允许所有出站流量
  → to-lport: 允许所有入站流量
  → 绕过 OVN 的源 IP 检查
```

**2. Business Pod 配置**
```
- 保留 Port Security (keep_port_security)
  → 维持基本的安全性,只允许发送自己的流量
  
- 添加 Stateless ACL (优先级 31821)
  → from-lport: 允许所有出站流量
  → to-lport: 允许所有入站流量
  → 允许接收来自任意外部 IP 的返回流量
```

**3. 智能 ACL 清理**
```
- 只删除指向不存在 pod 的孤儿 ACL
- 避免误删其他 pod 的正常 ACL
- 使用自定义优先级 31821 避免与系统 ACL 冲突
```

### Benefits (好处)

✅ **实现自定义出口路由**
- 突破 OVN EgressIP 的单子网限制
- 支持每个 namespace 使用不同的出口 IP
- 灵活的节点选择器配置

✅ **支持同节点部署**
- Gateway pod 和 business pod 可以在同一节点
- 通过 `accept_local` 参数解决本地路由问题

✅ **自动化管理**
- Controller 自动应用和清理 OVN 配置
- Pod 重启后自动重新配置
- 无需手动干预

### Risks and Trade-offs (坏处和权衡)

⚠️ **绕过 Network Policy**

**影响范围:**
- 使用 stateless ACL 会绕过 Kubernetes Network Policy 的部分功能
- 优先级 31821 高于 Network Policy 的 ACL(优先级通常在 1000-2000)
- **只影响配置了 patch 的 pod**(gateway pod 和 business pod)

**具体影响:**
```
Network Policy 功能      | Gateway Pod | Business Pod | 其他 Pod
--------------------|------------|-------------|--------
Egress 规则          | ❌ 被绕过    | ❌ 被绕过     | ✅ 正常
Ingress 规则         | ❌ 被绕过    | ❌ 被绕过     | ✅ 正常
Pod 间通信限制        | ❌ 无效     | ❌ 无效      | ✅ 正常
```

**缓解措施:**
- 将 gateway pod 部署在专用的 infra namespace
- 限制 business namespace 的 pod 数量
- 使用 RBAC 控制谁可以在这些 namespace 中创建 pod
- 在 gateway pod 中使用 iptables 实现额外的访问控制

⚠️ **Port Security 风险**

**Gateway Pod (Port Security 已清除):**
- 可以发送任意源 IP 的流量(IP spoofing)
- 可能被滥用进行网络攻击
- **缓解**: 使用 privileged SCC 限制,只允许特定 SA 使用

**Business Pod (Port Security 保留):**
- 仍然只能发送自己的 IP
- 保持了基本的安全性

⚠️ **OVN 数据库修改**

- 直接修改 OVN 数据库,绕过了 OpenShift 的标准流程
- 升级 OpenShift 时可能需要重新验证兼容性
- Controller 异常时可能留下孤儿 ACL(已通过智能清理缓解)

### Security Recommendations

1. **隔离 Gateway Namespace**
   ```bash
   # 使用专用的 infra namespace
   # 限制谁可以在这个 namespace 中创建 pod
   oc adm policy add-role-to-user admin user1 -n ns-egress-infra
   ```

2. **限制 Business Namespace**
   ```bash
   # 使用 ResourceQuota 限制 pod 数量
   # 避免大量 pod 绕过 Network Policy
   ```

3. **监控和审计**
   ```bash
   # 定期检查 ACL 配置
   # 监控异常的网络流量
   ```

- **自动应用**: Pod 创建时自动配置 OVN

- **智能管理**: 只删除孤儿 ACL,避免误删

### Automated Controller

Controller 自动化管理 OVN 配置和 APB 路由同步。完整源代码请参考:[controller.py](files/ovn.egressip/controller.py)

**核心功能:**

1. **APB 路由同步**
   - 监控 gateway pod 的 IP 变化
   - 自动更新 AdminPolicyBasedExternalRoute 的 nextHops
   - 防止手动修改被覆盖

2. **OVN 配置管理**
   - 自动为 gateway pod 清除 Port Security
   - 为 business pod 和 gateway pod 添加 stateless ACL
   - 智能清理孤儿 ACL(只删除指向不存在 pod 的规则)

3. **高可用特性**
   - 自动重启机制:遇到 API 错误自动恢复
   - 指数退避策略:避免持续失败时过度消耗资源
   - 双层异常处理:watch stream 和事件处理都有保护

4. **多租户支持**
   - 所有配置通过环境变量自定义
   - 支持管理多个 namespace 组合
   - 可配置的 ACL 优先级避免冲突

**配置方式:**

### 配置说明

通过环境变量,您可以:

1. **管理多个业务命名空间**:每个 controller 实例管理一个业务 namespace
2. **共享 infra namespace**:多个 controller 可以共享同一个 gateway infra namespace
3. **避免 ACL 冲突**:为每个 controller 使用不同的 `OVN_ACL_PRIORITY`
4. **灵活的标签选择**:通过 `GATEWAY_LABEL` 和 `BUSINESS_LABEL` 区分不同的 pod 组

### 环境变量完整列表

| 环境变量 | 默认值 | 说明 |
|---------|--------|------|
| `GATEWAY_NAMESPACE` | `ns-egress-infra` | Gateway pod 所在的命名空间 |
| `GATEWAY_LABEL` | `app=ns-blue-gateway` | Gateway pod 的标签选择器 |
| `BUSINESS_NAMESPACE` | `ns-blue` | 业务 pod 所在的命名空间 |
| `BUSINESS_LABEL` | `app=business-app` | 业务 pod 的标签选择器 |

| `OVN_POD_LABEL` | `app=ovnkube-node` | OVN pod 的标签选择器 |
| `OVN_CONTAINER` | `ovn-controller` | OVN 容器名称 |
| `OVN_ACL_PRIORITY` | `31821` | OVN ACL 规则的优先级 |
