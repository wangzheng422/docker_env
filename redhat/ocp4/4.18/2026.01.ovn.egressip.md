# OVN egressip limitation workaround

## Background

customer install a ocp 4.18 on 3rd part osp, using baremetal install method. and the osp has limitation of 10 elastic ip on each node. but the security require each namespace has a dedicate egress ip, and there are 40+ namespaces. and the elastic ip pools contains different subnets, and worker node has different associated relationship with elastic ip pools subnets. current ovn does not support node selector for egressip. and only single pool of egressip is supported. so we need to implement a workaround to support this requirement.

the basic idea is to use a gateway pod for each namespace to provide egress ip for the namespace. use ovn config to route the traffic to the gateway pod for the namespace pod. and use a tool pod to monitor the gateway pod's ip, and change ovn config's next hop ip when the gateway pod restart.

```python
# 文件名: controller.py
import os
import time
import threading
from kubernetes import client, config, watch

# 配置常量
# 配置常量
NAMESPACE = "ns-blue"
GATEWAY_NAMESPACE = "ns-egress-infra"
APB_NAME = "ns-blue-route"
GATEWAY_LABEL = "app=ns-blue-gateway"
GROUP = "k8s.ovn.org"
VERSION = "v1"
PLURAL = "adminpolicybasedexternalroutes"

def get_current_gateway_ips(v1):
    """获取当前所有 Running 状态的网关 Pod IP"""
    try:
        pods = v1.list_namespaced_pod(GATEWAY_NAMESPACE, label_selector=GATEWAY_LABEL)
        return sorted([p.status.pod_ip for p in pods.items if p.status.phase == "Running" and p.status.pod_ip])
    except Exception as e:
        print(f"Error listing pods: {e}")
        return []

def reconcile_apb():
    """核心调谐逻辑：对比并强制同步"""
    config.load_incluster_config()
    v1 = client.CoreV1Api()
    api = client.CustomObjectsApi()

    # 1. 获取当前网关真实的 Pod IP 列表 (期望状态)
    desired_ips = get_current_gateway_ips(v1)
    if not desired_ips:
        print("No running gateway pods found. Skipping sync.")
        return

    desired_formatted = [{"ip": ip} for ip in desired_ips]

    try:
        # 2. 读取当前 APB 资源的实际状态
        current_apb = api.get_cluster_custom_object(GROUP, VERSION, PLURAL, APB_NAME)
        current_static_hops = current_apb.get("spec", {}).get("nextHops", {}).get("static", [])

        # 3. 幂等性检查：对比期望 IP 和 实际 IP
        # 提取当前 IP 字符串进行对比
        current_ips_str = sorted([hop["ip"] for hop in current_static_hops if "ip" in hop])
        
        if current_ips_str == desired_ips:
            # 如果完全一致，直接退出，防止触发 Watch 的死循环
            return 

        # 4. 如果不一致，执行强制修正
        print(f"Detect deviation! Desired: {desired_ips}, Current in APB: {current_ips_str}. Correcting...")
        body = {"spec": {"nextHops": {"static": desired_formatted}}}
        api.patch_cluster_custom_object(GROUP, VERSION, PLURAL, APB_NAME, body)
        print("APB Successfully enforced.")

    except Exception as e:
        print(f"Reconciliation failed: {e}")

def watch_pods():
    """监听 Pod 变化"""
    v1 = client.CoreV1Api()
    w = watch.Watch()
    print("Started watching Pods...")
    for event in w.stream(v1.list_namespaced_pod, namespace=GATEWAY_NAMESPACE, label_selector=GATEWAY_LABEL):
        # 只要 Pod 状态有变（新增、删除、重启），执行调谐
        reconcile_apb()

def watch_apb():
    """监听 APB 资源变化（防止人为手动修改）"""
    api = client.CustomObjectsApi()
    w = watch.Watch()
    print("Started watching APB Resource...")
    # 注意：watch 的资源必须对应其 plural 名称
    for event in w.stream(api.list_cluster_custom_object, GROUP, VERSION, PLURAL):
        resource = event.get('object', {})
        if resource.get('metadata', {}).get('name') == APB_NAME:
            # 只要 APB 被修改（不管是人为还是程序），执行调谐
            # reconcile_apb 内部的对比逻辑会防止死循环
            reconcile_apb()

if __name__ == "__main__":
    config.load_incluster_config()
    
    # 启动时先执行一次强制同步
    reconcile_apb()

    # 使用多线程同时监听两类资源
    t1 = threading.Thread(target=watch_pods)
    t2 = threading.Thread(target=watch_apb)

    t1.start()
    t2.start()

    t1.join()
    t2.join()
```

## Troubleshooting

### Debugging with tcpdump

Since the gateway pod is minimal and might not have `tcpdump` installed (or valid subscriptions), use `oc debug node` to sniff from the host.

1.  **Get the Node Name and Container ID:**

    ```bash
    export POD_NAME=$(oc get pod -n ns-egress-infra -l app=ns-blue-gateway -o jsonpath='{.items[0].metadata.name}')
    export NODE_NAME=$(oc get pod -n ns-egress-infra $POD_NAME -o jsonpath='{.spec.nodeName}')
    export CONTAINER_ID=$(oc get pod -n ns-egress-infra $POD_NAME -o jsonpath='{.status.containerStatuses[0].containerID}' | sed 's/cri-o:\/\///')
    
    echo "Node: $NODE_NAME, ContainerID: $CONTAINER_ID"
    ```

2.  **Enter Node Debug Shell:**

    ```bash
    oc debug node/$NODE_NAME
    ```

3.  **Find PID and Enter Network Namespace (Inside Debug Shell):**

```bash
# Switch to host root
# chroot /host

# Find the PID of the container
export CID=<YOUR_CONTAINER_ID_FROM_STEP_1>
# Use grep/awk since jq might not be available on RHCOS
export PID=$(crictl inspect $CID  | grep '"pid":' | head -n 1 | awk '{print $2}' | tr -d ',')

# Verify PID
echo "Container PID: $PID"

# Enter the Pod's Network Namespace
# You can now run tcpdump (using the host's binary) inside the pod's interface context
exit

export PID=<the pid found>
nsenter -n -t $PID bash
```

4.  **Run tcpdump:**

    *   **Listen on eth0 (Overlay Traffic):**
        ```bash
        tcpdump -nn -i eth0
        ```
    *   **Listen on macvlan0 (Physical Traffic):**
        ```bash
        tcpdump -nn -i macvlan0
        ```


### Analysis Matrix

| eth0 (In) | macvlan0 (Out) | macvlan0 (In - Reply) | eth0 (Out - Reply) | Potential Cause |
| :--- | :--- | :--- | :--- | :--- |
| No  | - | - | - | **OVN Issue**: APB Route is not steering traffic to the gateway pod. Check APB resource and OVN traces. |
| Yes | No | - | - | **Forwarding Issue**: `iptables` FORWARD dropped, or Kernel `ip_forward` disabled. |
| Yes | Yes | No | - | **Physical Network**: Physical gateway dropping packets, or external server checking source IP (NAT failed?). |
| Yes | Yes | Yes | No | **Return Path**: `rp_filter` dropped the return packet, or `eth0` route missing causing loop. |
| Yes | Yes | Yes | Yes (but fail) | **OVN Port Security**: Unmatched Source IP. Packets leave `eth0` with External IP as source, but OVN drops them because they don't match Pod IP. |

### Verifying and Fixing OVN Port Security

Even if logs are silent, OVN by default drops packets where the Source IP doesn't match the Pod IP. Since our Gateway Pod is routing traffic from external IPs, we must disable this check.

1.  **Find the Logical Switch Port (LSP) name:**
    The LSP name is usually in the format `namespace_podname`.
    
    ```bash
    export LSP_NAME="ns-egress-infra_$(oc get pod -n ns-egress-infra -l app=ns-blue-gateway -o jsonpath='{.items[0].metadata.name}')"
    echo "LSP Name: $LSP_NAME"
    ```

2.  **Check Current Port Security:**
    Run this from any node (inside the `ovnkube-node` container):
    
    ```bash
    # Get any ovnkube pod
    export OVN_POD=$(oc get pods -n openshift-ovn-kubernetes -l app=ovnkube-node -o jsonpath='{.items[0].metadata.name}')
    
    # Check the port security
    oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl list Logical_Switch_Port $LSP_NAME
    ```
    *Look for the `port_security` field. If it has specific MAC/IPs, that's the blocker.*

3.  **Disable Port Security (The Fix):**
    
    ```bash
    # Clear the port_security column to allow all traffic
    oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl clear Logical_Switch_Port $LSP_NAME port_security
    ```


    # Clear the port_security column to allow all traffic
    oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl clear Logical_Switch_Port $LSP_NAME port_security

4.  **Verify Port Security is Empty:**
    
    ```bash
    oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl get Logical_Switch_Port $LSP_NAME port_security

    Go back to the business pod and `curl` again.

### Advanced: Detailed OVN Trace

To pinpoint exactly where the packet is dropped, we need a trace with full Layer 2 details. Copy and run this entire block:

```bash
# 1. Variables
export POD_NAME=$(oc get pod -n ns-egress-infra -l app=ns-blue-gateway -o jsonpath='{.items[0].metadata.name}')
export LSP_NAME="ns-egress-infra_$POD_NAME"
export LS_NAME=$(oc get pod -n ns-egress-infra $POD_NAME -o jsonpath='{.spec.nodeName}')
export OVN_POD=$(oc get pods -n openshift-ovn-kubernetes -l app=ovnkube-node --field-selector spec.nodeName=$LS_NAME -o jsonpath='{.items[0].metadata.name}')

# 2. Get Gateway Pod MAC (Source MAC)
export POD_MAC=$(oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl get Logical_Switch_Port $LSP_NAME addresses | tr -d '[]"')
# Validates parsing (sometimes it's "MAC IP", take just MAC)
export POD_MAC=$(echo $POD_MAC | awk '{print $1}')
echo "Pod MAC: $POD_MAC"

# 3. Get OVN Logical Router MAC (Destination MAC)
# We mean the OVN Logical Router that acts as the default gateway for the Pod's eth0.
# The packet leaves the Pod's eth0 and goes to this OVN Router.

# 3. Get OVN Logical Router MAC (Destination MAC)
# From 'ovn-nbctl show', we saw the router port is named "rtos-<node_name>".
# We can query its MAC directly.

# Extract the router port name (peer of the switch port)
export ROUTER_PORT_NAME="rtos-$LS_NAME"
echo "Router Port Name: $ROUTER_PORT_NAME"

# Get the MAC address of that Router Port from OVN DB
export ROUTER_MAC=$(oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl get Logical_Router_Port $ROUTER_PORT_NAME mac | tr -d '[]"')
export ROUTER_MAC=$(echo $ROUTER_MAC | awk '{print $1}') # Take the first MAC if multiple
echo "Router MAC: $ROUTER_MAC"

# If ROUTER_MAC is empty, you might need to check 'ovn-nbctl show' manually.


# 4. Construct Flow
# We simulate a packet:
#   - Arriving at the Switch Port (LSP) from the Pod
#   - Source MAC: Pod's eth0 MAC
#   - Dest MAC: OVN Router's MAC (because the pod is sending it to its gateway)
#   - Source IP: External IP (192.168.99.1) -> This is what triggers Port Security!
#   - Dest IP: Business Pod IP
export FLOW="inport == \"$LSP_NAME\" && eth.src == $POD_MAC && eth.dst == $ROUTER_MAC && ip4.src == $EXT_IP && ip4.dst == $TARGET_IP && ip.ttl == 64"

echo "Tracing Flow: $FLOW"
oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-trace $LS_NAME "$FLOW"
```



If the trace ends with `drop;` at `ls_in_l2_unknown`, it implies OVN doesn't recognize the `ROUTER_MAC` as a valid destination port on this switch.

**1. Verify Router Port MAC manually:**

```bash
# List all ports on the node's logical switch
oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-nbctl show $LS_NAME
```
*Look for a port with `type: router`. Use THAT port's address/MAC in the trace.*

**2. Final Verification - Business Pod tcpdump:**
If `ovn-trace` is confusing, the ultimate truth is on the Business Pod.

*   Find the node running `business-app`.
*   Debug that node (`oc debug node/<BUSINESS_NODE>`).
*   Find the Business Pod PID and enter its namespace (just like we did for the gateway).
*   Run `tcpdump -nn -i eth0 host 192.168.99.1`.
    *   **If you see packets:** Connectivity is working, `curl` fail is application layer.
    *   **If NO packets:** OVN is dropping it.

**4. Debugging the Destination Node (Business Node):**

**A. Sanity Check - Basic Reachability:**
Can the Gateway Pod even reach the Business Pod?
```bash
# Enter Gateway Pod
oc rsh -n ns-egress-infra deployment/ns-blue-gateway
# Ping Business Pod
ping -c 3 <BUSINESS_POD_IP> # e.g. 10.135.0.34
```
*   **If Ping Works:** The tunnel and routing are fine. The issue is likely specific to the return traffic (Source IP `192.168.99.1`) being dropped by a policy or conntrack.
*   **If Ping Fails:** Basic OVN routing is broken between these two nodes.

**B. Host Level Capture (Geneve):**
Did the return packet even reach the Business Node?
```bash
# Debug Business Node
oc debug node/$BUS_NODE

# Capture on the 'any' interface or physical interface to see Geneve
# Filter for Outer UDP 6081 (Geneve) and Inner IP 192.168.99.1
# Note: tcpdump filters on the outer header usually.
# To see inner, we capture all geneve and grep, or just use 'any'.
tcpdump -nn -i any port 6081 -v | grep "192.168.99.1"
```

**C. Check OVN Logs on Business Node:**
    Port Security on the *destination* (Business Pod) only checks destination IP (which matches). But maybe something else is dropping it.

```bash
# Find ovnkube-node on that node
export OVN_POD_BUS=$(oc get pods -n openshift-ovn-kubernetes -l app=ovnkube-node --field-selector spec.nodeName=$BUS_NODE -o jsonpath='{.items[0].metadata.name}')

# Check logs
oc logs -n openshift-ovn-kubernetes $OVN_POD_BUS -c ovn-controller | grep "port_sec"
```

**D. Check Conntrack on Business Node:**
    The return packet must match an existing flow (SYN sent). 
    ```bash
    oc debug node/$BUS_NODE
    # Inside debug shell:
    conntrack -L | grep 192.168.99.1
    ```
    *   If you see `[UNREPLIED]`, the return packet isn't reaching the conntrack engine.
    *   If you see `[ASSURED]` or generally established, but tcpdump sees nothing, it's a veth/CNI issue.

**5. One last desperate check - MTU:**
If `192.168.99.1` sends a large packet (with geneve overhead), it might be dropped.
Try `curl` with small MSS?
(Unlikely for simple HTTP GET, but possible).
