# Identifying Pods Affected by Secret Rotation in OpenShift

## 1. Introduction

In a dynamic OpenShift Container Platform (OCP) environment, managing the lifecycle of TLS certificates and other secrets is a critical operational task. When a secret, particularly a TLS secret, is rotated or updated, it is essential to identify all workloads (Pods) that consume it. Pods that mount secrets as volumes or use them in environment variables often need to be restarted to pick up the new secret content.

Customers frequently require a comprehensive list of all pods that will be affected by a secret rotation to plan for potential service interruptions and ensure a smooth transition. This document outlines a non-disruptive method and provides a script to generate this list by analyzing pod specifications across the entire cluster.

## 2. Methodology

The core principle behind this approach is that if a pod is restarted during a secret rotation, it's likely because it directly consumes the secret's content. The OpenShift control plane or an operator might trigger this restart to force the pod to reload its configuration, including the updated secret.

Therefore, by systematically scanning the YAML definition of every running pod, we can identify dependencies on specific secrets. The provided script automates this process by checking for secret references in three key areas of a pod's specification:

1.  **`spec.volumes`**: Pods mounting a secret as a data volume.
2.  **`spec.containers[*].envFrom`**: Pods sourcing all key-value pairs from a secret as environment variables.
3.  **`spec.containers[*].env`**: Pods sourcing specific keys from a secret as environment variables.

The script focuses on secrets of type `kubernetes.io/tls` and `Opaque`, as these are most commonly associated with certificate rotation and sensitive configuration data.

## 3. Analysis Script

The following Bash script iterates through all relevant secrets in the cluster and, for each secret, queries for pods in the same namespace that reference it.

```bash
#!/bin/bash

# This script performs a non-disruptive analysis to identify pods with dependencies on TLS or Opaque secrets.

echo "Starting non-disruptive analysis of Secret dependencies..."
echo "================================================================================"

# Retrieve all Secrets of type kubernetes.io/tls or Opaque, formatted as "namespace secret_name".
# The jsonpath filter uses separate 'range' clauses for each type, as a direct OR (||) is not supported for filtering on multiple type values in a single clause.
oc get secret -A \
  -o jsonpath='{range .items[?(@.type=="kubernetes.io/tls")]}{.metadata.namespace}{" "}{.metadata.name}{"\n"}{end}{range .items[?(@.type=="Opaque")]}{.metadata.namespace}{" "}{.metadata.name}{"\n"}{end}' | \
sort -u | \
while read -r SECRET_NAMESPACE SECRET_NAME; do
  
  echo "[INFO] Checking Secret: '$SECRET_NAME' in namespace: '$SECRET_NAMESPACE'"

  # Find all pods in the namespace that reference this Secret using a jq query.
  AFFECTED_PODS=$(oc get pods -n "$SECRET_NAMESPACE" -o json | jq -r --arg SECRET_NAME "$SECRET_NAME" '
    .items[] |
      select(
        # Condition 1: Check for secret usage in volumes
        (any(.spec.volumes[]?; .secret?.secretName == $SECRET_NAME)) or

        # Condition 2: Check for secret usage in envFrom references
        (any(.spec.containers[]?; any(.envFrom[]?; .secretRef?.name == $SECRET_NAME))) or

        # Condition 3: Check for secret usage in env valueFrom references
        (any(.spec.containers[]?; any(.env[]?; .valueFrom?.secretKeyRef?.name == $SECRET_NAME)))
      ) | .metadata.name
  ')

  # If affected pods are found, format and print the list.
  if [ -n "$AFFECTED_PODS" ]; then
    echo "  └── Affected Pods:"
    echo "$AFFECTED_PODS" | while read -r POD_NAME; do
      echo "      - $POD_NAME"
    done
  else
    echo "  └── No affected pods found."
  fi
done

echo "================================================================================"
echo "Analysis complete."
```

## 4. Execution and Expected Output

To run the analysis, save the script to a file (e.g., `find_secret_deps.sh`), make it executable (`chmod +x find_secret_deps.sh`), and run it while logged into your OpenShift cluster with sufficient permissions.

The output will be a list of secrets, each followed by the pods that depend on it.
