## planning

Here is the solution to integrate between ansible automation platform(aap) with service.now.

1. set up in ocp, aap, demo workload, and webhook in service.now
2. alert trigger in ocp, which monitoring deployment's replica less than 2, then trigger ansible eda
3. eda's rulebook will 
   1. get pods info, pods log, alert configuration, alert content, and send them service.now to create incident.
   2. send all infomation to deepseek, and get suggested solution playbook back.
   3. save the ai gen playbooks into repo's new branch, 
   4. create a change request in service.now, this will need approve in service.now
4. service.now workflow will promote to approve to review
5. if approved in service.now for the change request, service.now will call ansible playbook (eda in aap again?)
   1. call ansible playbook to merge into production branch

There is a webhook defined in github, if the branch merge, it will trigger a job, which will run a job template, and the ansible script from deepseek will be triggered.

## **Revised and Improved Workflow**

Here is a more robust and secure version of your workflow:

1.  **Monitoring & Alerting (No Change):** An alert is triggered in OpenShift (replica count < 2).
2.  **EDA Trigger (No Change):** The alert is sent to an AAP Webhook, triggering an EDA rulebook.
3.  **EDA Rulebook Actions:**
    * Gather diagnostic data (pod logs, alert info, etc.).
    * Call the Deepseek AI API with the data to **generate a *suggested* playbook**.
    * Create an **Incident** in ServiceNow, populating it with all the diagnostic data and the **full text of the AI-generated playbook**.
4.  **ServiceNow Incident & Change Request:**
    * An engineer reviews the Incident. If remediation is required, they create a **Change Request (CR)**.
    * The CR is linked to the Incident and **must include the playbook code for review**.
    * The CR goes through the standard approval workflow (peer review, manager approval). **Approvers are explicitly approving the code.**
5.  **Remediation Trigger (Optimized):**
    * Once the CR is **approved** in ServiceNow, its workflow makes a **direct API call** to a pre-defined **AAP Job Template**.
    * This Job Template is designed to run the remediation. It takes the playbook code (or a Git branch name) as a parameter.
6.  **Ansible Job Execution:**
    * The AAP Job Template runs the approved playbook to scale the deployment back to the desired number of replicas.
    * Upon successful execution, the job updates the ServiceNow Change Request and Incident to a "Resolved" state.

## **优化后的建议工作流 (Recommended and Optimized Workflow)**

Here is the solution to integrate between ansible automation platform(aap) with service.now

1.  **告警与事件驱动（不变）**: OCP监控到副本数异常，触发告警，调用AAP EDA的Webhook。
2.  **EDA处理与生成建议（不变）**: EDA规则手册运行：
    * 收集所有诊断信息（Pod日志、告警详情等）。
    * 调用Deepseek API，生成修复问题的Playbook。
    * **将AI生成的Playbook内容推送到一个新的Git分支**（例如 `feature/fix-replicas-123`）。
    * **在GitHub中基于这个新分支自动创建一个Pull Request (PR)**，目标是合并到`main`分支。
    * 在ServiceNow中创建一个变更请求（Change Request）。
3.  **ServiceNow审批（优化）**:
    * 在ServiceNow的变更请求中，填入所有诊断信息。
    * **最关键的一步：将上一步创建的GitHub Pull Request的URL链接直接放入变更请求的描述或一个专门的字段中。**
    * 审批流程启动。审批者在ServiceNow中点击链接，审查PR中的代码。
4.  **批准与执行（核心优化点）**:
    * 当变更请求在ServiceNow中获得最终批准后，ServiceNow的Workflow会通过API**直接调用AAP中一个特定的作业模板 (Job Template)**，并把PR的URL或分支名作为参数传给它, 以及需要运行的playbook名字和运行目录作为额外参数。
    * 这个AAP作业模板会执行以下一系列**线性任务**：
        1.  **运行一个脚本来通过API合并GitHub中的Pull Request**。
        2.  **更新AAP中的项目 (Project)**，确保它从Git拉取了包含最新代码的`main`分支。
        3.  **从更新后的项目中，运行那个刚刚被合并的Playbook**，对OCP中的应用进行修复。
        4.  执行成功后，通过API**更新ServiceNow中的变更请求状态**为“成功/已完成”。

---

实际上，在AAP中实现这个流程的最佳方式是使用 **Workflow Job Template**。这个Workflow本身就关联**Project A（编排器）**，并且由ServiceNow触发。

这个Workflow的图形化界面会是这样：

1.  **(Start)**: ServiceNow通过API调用，启动这个Workflow，并传入PR链接等`extra_vars`。
2.  **节点1: Merge PR**: 一个简单的Job Template，使用Project A中的Playbook，执行合并PR的操作。
3.  **节点2: Sync Project B**: 这是一个**Project Sync**类型的节点。你不需要写Playbook来做这件事，在Workflow里直接选择**Project B**并命令它“同步”即可。这一步会在上一步成功后（on success）自动运行。
4.  **节点3: Run Remediation**: 这是一个**Job Template**类型的节点，它指向我们之前定义的**Job Template B**（它使用Project B，并运行修复Playbook）。它也会在上一步成功后自动运行。
5.  **节点4: Update ServiceNow**: 最后，一个使用Project A中Playbook的Job Template，负责将执行结果回调给ServiceNow。

这种方式更加清晰、模块化，并且是AAP为解决此类复杂依赖关系而设计的标准功能。

```js
(function() {
    /**
     * 此函数用于从工作日志中解析 playbook 的路径。
     * 它会从最新的日志开始，逐行查找关键字 "playbook_to_run:"。
     * @returns {string|null} - 如果找到，则返回 playbook 路径；否则返回 null。
     */
    function getPlaybookFromWorkNotes() {
        // 获取所有工作日志条目，-1代表获取全部。返回的是一个长字符串，各项由 \n\n 分隔。
        var workNotes = current.work_notes.getJournalEntry(-1);
        
        // 按行分割日志内容
        var lines = workNotes.split('\n');

        // 从最新的日志开始，逐行遍历
        for (var i = 0; i < lines.length; i++) {
            var currentLine = lines[i].trim(); // 清除行首尾的空格

            // 检查当前行是否以 "playbook_to_run:" 开头（不区分大小写）
            if (currentLine.toLowerCase().startsWith('playbook_to_run:')) {
                // 找到了关键字，现在提取冒号后面的值
                var parts = currentLine.split(':');
                // 移除第一部分（即关键字 "playbook_to_run"），然后将剩余部分重新组合
                // 这样做是为了防止 playbook 路径本身也包含冒号
                parts.shift(); 
                var playbookPath = parts.join(':').trim(); // 重新组合并清除首尾空格
                
                // 确保提取到的路径不为空
                if (playbookPath) {
                    workflow.info("在 Work Notes 中找到 Playbook: " + playbookPath);
                    return playbookPath; // 返回找到的路径
                }
            }
        }
        
        // 如果遍历完所有行都没有找到，则返回 null
        workflow.warn("在 Work Notes 中未找到 'playbook_to_run:' 关键字。");
        return null;
    }

    // --- 主执行逻辑 ---
    var playbookToRun = getPlaybookFromWorkNotes();

    // 只有在成功提取到 playbook 路径时，才执行 Webhook 调用
    if (playbookToRun) {
        try {
            var r = new sn_ws.RESTMessageV2('aap webhook demo', 'aap post');

            // r.setStringParameterNoEscape('playbook_to_run', current.variables.script_to_run); 

            var currentDateTime = new GlideDateTime().getValue(); // Gets current time in 'yyyy-MM-dd HH:mm:ss' format
            r.setStringParameterNoEscape('commit_timestamp', currentDateTime);

            
            // 关键：将从 Work Notes 中提取的 playbook 路径作为 'script_to_run' 参数的值
            r.setStringParameterNoEscape('playbook_to_run', playbookToRun);
            
            // 在您的 REST Message 中，也需要有 ${commit_timestamp} 这个变量
            r.setStringParameterNoEscape('commit_timestamp', new GlideDateTime().getValue());

            var response = r.execute();
            var httpStatus = response.getStatusCode();

            if (httpStatus == 200) {
                workflow.info("成功发送数据到 Webhook，Playbook: " + playbookToRun);
            } else {
                workflow.error("发送数据到 Webhook 失败。状态码: " + httpStatus);
            }

        } catch (ex) {
            var message = ex.getMessage();
            workflow.error("调用 Webhook 时发生异常: " + message);
        }
    } else {
        // 如果没有找到 playbook，在这里可以定义相应的处理逻辑，例如结束工作流或设置状态
        workflow.info("因未在 Work Notes 中找到 playbook，Webhook 调用被跳过。");
    }
})();
```
