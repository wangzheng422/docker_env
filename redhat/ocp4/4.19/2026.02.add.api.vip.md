# OCP 4.19 Agent-based Installation (ABI)：增加 API / Ingress VIP 的深度研究与解决方案

在 OpenShift 4.19 (ABI) 裸金属环境下，API VIP 和 Ingress VIP 的管理逻辑具有高度的原子性和不可变性。本页将结合用户提供的 `keepalived.yaml` 源码，详细列出使用 **MetalLB** 实现 API VIP 扩展的完整配置案例。

## 1. 深度分析：keepalived.yaml 源码级解析

根据 Master 节点上 `/etc/kubernetes/manifests/keepalived.yaml` 的定义，其分层管理的逻辑决定了任何手动修改都会被覆盖。

### 1.1 静态 Pod 定义片段：

```yaml

    - render

```

**结论**：文件的哈希值受 Cluster Network Operator (CNO) 严密监控。

## 2. “正向方案”：使用 MetalLB 扩展 API VIP

如果您决定通过 MetalLB 来宣告一个新的 API VIP（例如 `192.168.99.17`），请按照以下配置示例操作。

### 2.1 MetalLB 地址池配置 (IPAddressPool)
首先定义用于 API 的独立 IP 地址池。

```yaml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: api-vip-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.99.17/32 # <--- 您希望增加的新 API VIP
  autoAssign: false    # 建议设为 false，防止被业务 Service 抢占
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: api-vip-adv
  namespace: metallb-system
spec:
  ipAddressPools:
  - api-vip-pool
```

### 2.2 创建 API 负载均衡服务 (Service & Endpoints)
由于 API Server 本身是静态 Pod，通常不直接受 Service 选择器控制。您可以通过创建一个指向 Master 节点 IP 的透明 Service 来实现。

> [!IMPORTANT]
> **关键坑点**：如果 `Service` 定义了 `name` 端口（如下方的 `api-server`），则 `Endpoints` 中的端口定义也必须包含**完全一致**的 `name`，否则关联会失败，导致后端列表为空。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api-external-lb
  namespace: openshift-config
spec:
  type: LoadBalancer
  ports:
  - port: 6443
    targetPort: 6443
    name: api-server # <--- 定义了端口名称
  loadBalancerIP: 192.168.99.17 # <--- 业务使用的 VIP
---
# 手动定义 Endpoints，指向三台 Master 节点的物理 IP
apiVersion: v1
kind: Endpoints
metadata:
  name: api-external-lb
  namespace: openshift-config
subsets:
  - addresses:
      - ip: 192.168.99.23
      - ip: 192.168.99.24
      - ip: 192.168.99.25
    ports:
      - port: 6443
        name: api-server # <--- 必须补上这个名称，否则无法与 Service 关联！
```

## 3. 故障排查：为什么会报 Connection refused？

根据您的 `arp -an` 输出：
`? (192.168.99.17) at 00:50:56:8e:2a:32 [ether] on enp1s0`
这说明 **MetalLB 的二层宣告 (ARP) 已经成功了**，流量能够到达节点。之所以 `curl` 报拒绝连接，通常是由于以下原因：

### 3.1 原因分析：Service 后端为空 (Endpoints Mismatch)
在 Kubernetes 逻辑中，如果 `Service` 定义了 Named Port，但 `Endpoints` 未能匹配，该 Service 的状态就是无效的。
- **表现**：底层 OVN/iptables 规则不会生成转发条目，请求到达节点后会被协议栈直接回复 `RST`。
- **验证**：运行 `oc describe svc api-external-lb -n openshift-config`，如果 `Endpoints` 行为空或 `<none>`，则证明是此问题。


## 4. 终极“避坑”逻辑：DNS 伪装

即使 MetalLB 成功宣告了 `.17`，**证书校验**依然是最后一道关卡。

### 4.1 为什么必须用域名访问？
- **直接用 IP 访问**：`oc login https://192.168.99.17:6443` -> **失败**。原因是个证书 SAN 列表不包含 `.17`。
- **通过域名访问**：
    1.  配置外部 DNS，将 `api.<cluster>.<domain>` 解析到新 VIP `192.168.99.17`。
    2.  客户端执行 `oc login https://api.<cluster>.<domain>:6443`。
    3.  **结果：成功**。客户端验证的是 Hostname，只要域名对得上，它就不在乎中间经过了哪个 IP。

## 4. 总结

| 方案 | 操作 | 结果 |
| :--- | :--- | :--- |
| **MetalLB** | 创建 IPAddressPool + LoadBalancer Service | **成功宣告网络 IP** |
| **DNS 配合** | 将 API Domain 指向 MetalLB VIP | **成功通过证书校验** |
| **系统修改** | 改 `keepalived.yaml` 或 `Infrastructure` | **失败 (被回滚或拒绝)** |

**结论**：MetalLB 提供网络连接性，DNS 解析提供身份合法性。二者结合是在 OCP 4.x ABI 中扩展 API VIP 的最佳实践。
