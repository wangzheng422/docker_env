# Deep Dive: BGP Ingress Traffic Flow with MetalLB in OpenShift 4.19

## Overview

In **OpenShift 4.19**, using **MetalLB** with the **FRR-K8s** driver enables BGP-based service publication (Ingress). Unlike Egress Services, Ingress traffic focuses on how to bring external traffic into the cluster via BGP routing and distribute it evenly across backend Pods. This document explores the complete process from BGP route advertisement, through host-level `iptables` interception, to OVN logical flow forwarding.

---

## 1. Validation Topology

This validation was performed on a 3-node compact cluster, where all nodes have both `master` and `worker` roles.

*   **Node IPs**: `192.168.99.23`, `192.168.99.24`, `192.168.99.25`
*   **Service LoadBalancer IP (VIP)**: `192.168.66.100`
*   **ClusterIP**: `172.22.88.148`
*   **Backend Pods**:
    *   Pod 1: `10.132.0.39` (running on `master-02-demo`)
    *   Pod 2: `10.133.0.4` (running on `master-03-demo`)

## 2. Infrastructure Configuration

### 2.1 MetalLB Basic Configuration and BGP Advertisement

In addition to the address pool, we need to explicitly configure `BGPPeer` to establish neighbor relationships with the upstream router.

```yaml
# BGPPeer Definition: Establishing BGP neighbor relationship
apiVersion: metallb.io/v1beta2
kind: BGPPeer
metadata:
  name: peer-sample1
  namespace: metallb-system
spec:
  peerAddress: 192.168.99.12
  peerASN: 64512
  myASN: 64512
  peerPort: 179

---
# IPAddressPool Definition
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: egress-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.66.100-192.168.66.100

---
# BGPAdvertisement Definition: Selecting all master nodes for advertisement
apiVersion: metallb.io/v1beta1
kind: BGPAdvertisement
metadata:
  name: egress-identity-bgp-adv
  namespace: metallb-system
spec:
  ipAddressPools:
  - egress-pool
  nodeSelectors:
  - matchLabels:
      node-role.kubernetes.io/master: ""
```

## 3. Traffic Deep Dive

When an external packet with destination `192.168.66.100:8080` reaches a cluster node, its processing path involves close collaboration between host-level `iptables` and OVN.

### 3.1 Step 1: Host-level Iptables DNAT

In the host's `nat` table, OVN-Kubernetes sets up interception rules to redirect traffic arriving at the VIP to the ClusterIP.

```bash
# Check iptables on master-01-demo node
oc debug node/master-01-demo -- chroot /host bash -c 'iptables -t nat -S | grep 192.168.66.100'
# Output:
# -A OVN-KUBE-EXTERNALIP -d 192.168.66.100/32 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.22.88.148:8080
```
- **Evidence**: External traffic is converted to ClusterIP at the host level before entering the OVN logical network.

### 3.2 Step 2: OVN Logical Flow Processing

After DNAT, the destination address becomes `172.22.88.148`. Load Balancing (LB) rules for this ClusterIP and VIP are pre-configured in the OVN Southbound DB (SBDB).

```bash
# Query OVN Logical Flows
OVN_NODE_01_POD=$(oc get po -n openshift-ovn-kubernetes -l app=ovnkube-node -o wide | grep "master-01-demo" | awk '{print $1}')
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovn-sbctl lflow-list | grep -E "172.22.88.148|192.168.66.100"
# Logical Flow Evidence:
# table=13(ls_in_lb           ), priority=120  , match=(ct.new && ip4.dst == 172.22.88.148 && tcp.dst == 8080), action=(reg4 = 172.22.88.148; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)
```

### 3.3 Step 3: OVN-to-OVS Flow Translation Mechanism

The `ovn-controller` is responsible for downloading (translating) the above logical flows into OVS `OpenFlow` rules.

**Core Logic:**
1.  **UUID Mapping**: Each entry in the OVN logical flow table has a unique UUID. The `ovn-controller` calculates a hash of this UUID and uses it as the `cookie` for the OVS flow table.
2.  **Pipeline Conversion**: OVN Table IDs map to specific OVS Tables. For instance, the ingress table of a Logical Switch (LS) port typically corresponds to OVS logic starting from Table 0.

```bash
# 1. Reverse Query: Looking for the corresponding logical flow in the OVN Southbound DB (with UUID output)
# Here we search for ClusterIP 172.22.88.148
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c sbdb -- ovn-sbctl --uuid lflow-list | grep -B 1 "172.22.88.148"
# Result:
# uuid=0x93f7000b, table=13(ls_in_lb           ), priority=120  , match=(ct.new && ip4.dst == 172.22.88.148 && tcp.dst == 8080), action=(reg4 = 172.22.88.148; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)

# 2. Locate the OVS Flow on the physical node using the Cookie (the first 8 digits of the UUID)
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovs-ofctl dump-flows br-int | grep "cookie=0x93f7000b"
# Result:
# cookie=0x93f7000b, duration=17039.689s, table=21, n_packets=0, n_bytes=0, idle_age=17039, priority=120,ct_state=+new+trk,tcp,metadata=0x2,nw_dst=172.22.88.148,tp_dst=8080 actions=load:0xac165894->NXM_NX_XXREG1[96..127],load:0x1f90->NXM_NX_XXREG0[32..47],group:133


oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovs-ofctl dump-groups br-int | grep "group_id=133"
#  group_id=133,type=select,selection_method=dp_hash,bucket=bucket_id:0,weight:100,actions=ct(commit,table=22,zone=NXM_NX_REG13[0..15],nat(dst=10.132.0.39:8080),exec(load:0x1->NXM_NX_CT_MARK[1])),bucket=bucket_id:1,weight:100,actions=ct(commit,table=22,zone=NXM_NX_REG13[0..15],nat(dst=10.133.0.4:8080),exec(load:0x1->NXM_NX_CT_MARK[1]))
```

#### 3.3.1 Deep Technical Analysis

1.  **The Link Between Cookie and UUID**: 
    The `cookie=0x93f7000b` in the OVS flow table exactly corresponds to the OVN Logical Flow UUID `0x93f7000b` (the first 8 digits). This mapping mechanism proves that `ovn-controller` persists logical-layer identifiers into physical-layer `cookies` during translation. This is crucial for troubleshooting: by using the cookie from a physical flow, we can directly trace back to the OVN Logical Flow.

2.  **OVS Flow Match Interpretation**:
    *   `ct_state=+new+trk`: This indicates matching a new connection that is already being tracked by the `conntrack` state machine.
    *   `nw_dst=172.22.88.148`, `tp_dst=8080`: Matches the target ClusterIP and port. Since traffic has already undergone DNAT by the host `iptables` before entering OVN, the match here is against the translated internal address.

3.  **Action Execution and Load Balancing (Actions & Group)**:
    *   `group:133`: Traffic is handed over to OVS Group 133 for processing. In OVN, `ct_lb` actions are typically translated into `type=select` OVS Groups to leverage OpenFlow's distribution capabilities.
    *   `selection_method=dp_hash`: Inside Group 133, the kernel's `dp_hash` algorithm is used to perform load balancing based on the five-tuple.
    *   `nat(dst=10.132.0.39:8080)`: This is the final action executed at the physical layer, where the packet's destination is translated from the ClusterIP to the backend Pod IP.

4.  **The Source of UUID (UUID Lifecycle)**:
    *   **NB DB**: After a user defines a Service, OVN-Kubernetes creates logical objects in the Northbound DB (NBDB).
    *   **SB DB**: `ovn-northd` monitors changes and translates them into `Logical_Flow` entries in the Southbound DB (SBDB).
    *   **UUID Generation**: When `ovn-northd` inserts a `Logical_Flow`, the **OVSDB Server** automatically generates a unique `_uuid` according to the RFC 4122 standard and persists it.
    *   **Cookie Mapping**: The node's `ovn-controller` synchronizes the `Logical_Flow` and, when deploying the physical flow, assigns the first 32 bits of the UUID to the `cookie` field.

## 5. Conclusion

In OpenShift 4.19, the MetalLB-based BGP Ingress solution achieves efficient traffic ingress through two-level collaboration between `iptables` and `OVN`:
1.  **BGP** solves the problem of how traffic is routed to physical nodes.
2.  **Iptables** quickly performs the initial de-mapping from VIP to ClusterIP.
3.  **OVN Logical Flows** provide high-performance service discovery and load balancing based on OVS state tracking.

This architecture avoids dependency on a single ingress node, achieving true cluster-level inbound traffic distribution.
