# 技术深度解析：OpenShift 4.19 中基于 BGP 与 OVN 的分布式 Egress IP 方案实现

## 1. 摘要 (Abstract)

在现代云原生架构中，精确控制集群外部访问流量的出口（Exit Point）是确保企业网络安全与合规性的核心环节。OpenShift 4.19 引入了更为成熟的基于 OVN-Kubernetes 的分布式网络架构。本文旨在深入探讨如何结合 **BGP (Border Gateway Protocol)**、**OVN-Kubernetes** 与 **Egress IP** 技术，构建一个灵活、高性能且具备故障转移能力的出口流量管理方案。

我们将通过一个完整的实验环境，演示如何配置 BGP 宣告 Egress IP 路由，并从底层 **OVS 流表**、**Linux 内核策略路由 (PBR)** 以及 **Geneve 隧道封装** 等维度，拆解流量劫持与“Tromboning”（长臂管辖/流量回送）效应的实现机制。

---

## 2. 实验环境架构 (Lab Environment Architecture)

为验证本方案的技术可行性，我们设计并构建了一套基于 KVM/libvirt 虚拟化平台的模拟环境。实验部署在一台运行 CentOS 9 的 Baremetal 宿主机上，通过 `br-ocp` 网桥实现内部互联。

### 2.1 拓扑说明
- **宿主机**: Baremetal CentOS 9 (IP: `192.168.99.1`)
- **内部网段**: `192.168.99.0/24`

### 2.2 核心组件细节
1.  **OpenShift 4.19 虚拟化集群**:
    - **节点规模**: 3 个融合节点（Compact Nodes，兼具 Master 与 Worker 角色）。
    - **IP 地址池**: `192.168.99.23 ~ 192.168.99.25`。
    - **Egress IP 子网**: `192.168.66.100/24`（属于逻辑隔离的外部网络）。
    - **功能组件**: 启用 OVN-Kubernetes 默认 CNI，部署 MetalLB/FRR-K8s 以支持 BGP 能力。
2.  **上游路由器 (KVM Router - CentOS 9)**:
    - 模拟数据中心骨干交换机，运行软件态 **FRR (Free Range Routing)**。
    - **内网接口 `eth0`**: `192.168.99.12`（对接 OCP 集群）。
    - **外网接口 `eth1`**: `192.168.55.12`（对接业务服务器）。
3.  **目标服务器 (KVM Server - CentOS 9)**:
    - 模拟受访的外部生产业务系统。
    - **接口 `eth0`**: `192.168.55.13`，默认网关指向 Router (`192.168.55.12`)。

## 3. 基础架构配置 (Infrastructure Configuration)

### 3.1 路由器 (FRR) 节点配置
作为 BGP 邻居，Router 节点需要开启内核数据包转发，并配置 iBGP 监听来自 OpenShift 节点的路由宣告。

```bash
# 1. 安装基础路由组件
sudo dnf install -y frr

# 在启动之前，必须在 daemons 文件中显式启用 bgpd 进程
sudo sed -i 's/^bgpd=no/bgpd=yes/' /etc/frr/daemons

sudo systemctl enable --now frr

# 2. 开启内核 IPv4 转发能力
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.d/99-ipforward.conf
sudo sysctl -p /etc/sysctl.d/99-ipforward.conf

# 3. 编排 FRR 核心配置文件
cat <<EOF | sudo tee /etc/frr/frr.conf
frr defaults traditional
log syslog informational
no ipv6 forwarding
!
router bgp 64512
 bgp router-id 192.168.99.12
 
 ! 配置分别对接 OCP 集群内各节点的 iBGP 邻居
 neighbor 192.168.99.23 remote-as 64512
 neighbor 192.168.99.24 remote-as 64512
 neighbor 192.168.99.25 remote-as 64512

 ! 确保 iBGP 等价多路径 (ECMP) 与网络宣发在 address-family 内配置
 address-family ipv4 unicast
  network 192.168.55.0/24
  maximum-paths ibgp 4
 exit-address-family
!
line vty
!
EOF

# 4. 重启 FRR 服务使配置生效
sudo systemctl restart frr
```

### 3.2 目标服务器 (External Server) 配置
Server 作为流量接收端，仅需配置回程路由指向 Router。为验证 Egress IP 的透明性，我们启动 Python HTTP 服务并开启抓包。

```bash
# 配置静态路由，确保回程流量通过 Router 指引向 Egress IP 网段
sudo ip route add 192.168.66.100 via 192.168.55.12

# 确认路由表状态
ip r
# default via 192.168.99.1 dev enp1s0 proto static metric 100
# 192.168.55.0/24 dev enp1s0 proto kernel scope link src 192.168.55.13 metric 100
# 192.168.66.100 via 192.168.55.12 dev enp1s0
# 192.168.99.0/24 dev enp1s0 proto kernel scope link src 192.168.99.13 metric 100

# 在后台启动辅助测试的 Http 监听点
# 同时监听 80 和 8080 端口，验证 Egress IP 不受限于特定 Service 端口
nohup python3 -m http.server 80 &
nohup python3 -m http.server 8080 &

# 使用 tcpdump 实时观测来自 Egress IP (192.168.66.100) 的访问报文
sudo tcpdump -i any 'tcp port 80 or tcp port 8080' -n
```

## 5. Egress IP 与路由宣告实现 (Egress IP Implementation)

### 5.1 节点角色定义
首先，我们需要标识哪些节点有资格承载 Egress IP 流量。

```bash
# 为所有节点打上 egress-assignable 标识
# OVN-K 通过此标签挑选谁有资格托管外部 IP
oc label node --all k8s.ovn.org/egress-assignable="" --overwrite
# node/master-01-demo labeled
# node/master-02-demo labeled
# node/master-03-demo labeled
```

### 5.2 配置 BGP 邻居与路由广告 (RouteAdvertisements)
在 OpenShift 4.19 中，我们使用原生的 `RouteAdvertisements` CRD 来管理 Egress IP 的 BGP 宣告。

```bash
# 1. 配置集群级 BGP 邻居信息 (FRRConfiguration)
cat <<EOF | oc apply -f -
apiVersion: frrk8s.metallb.io/v1beta1
kind: FRRConfiguration
metadata:
  labels:
    use-for-advertisements: "true"
  name: bgp-core-router
  namespace: openshift-frr-k8s
spec:
  bgp:
    bfdProfiles:
    - detectMultiplier: 3
      name: fast-bfd
    routers:
    - asn: 64512
      neighbors:
      - address: 192.168.99.12
        asn: 64512
        bfdProfile: fast-bfd
        disableMP: true
        dualStackAddressFamily: false
        toAdvertise:
          allowed:
            mode: all
        toReceive:
          allowed:
            mode: filtered
            prefixes:
            - prefix: 192.168.55.0/24
EOF

# 2. 定义路由广告策略，指定宣告 EgressIP
cat <<EOF | oc apply -f -
apiVersion: k8s.ovn.org/v1
kind: RouteAdvertisements
metadata:
  name: default
spec:
  advertisements:
  - EgressIP
  nodeSelector: {}
  frrConfigurationSelector:
    matchLabels:
      use-for-advertisements: "true"
  networkSelectors:
  - networkSelectionType: DefaultNetwork
EOF
```

### 5.3 部署 Egress IP 资源
分配静态 IP `192.168.66.100` 给 `demo-egress` 命名空间。

### 6.6 Egress IP 的 ARP 行为与交换机 MAC 地址学习

在 BGP Egress IP 场景中，上游 FRR 路由器**不会**对 `192.168.66.100` 发起 ARP 请求 —— 它通过 BGP 路由表（`192.168.66.100/32 via 192.168.99.24`）进行 L3 转发，只需 ARP 解析下一跳 `192.168.99.24` 的 MAC 地址。

然而，由于所有 OCP 节点的 `br-ex` 上都配置了 `192.168.66.x/24` 辅助地址，Linux 内核认为 `192.168.66.100` 与本机在同一 L2 网段，因此节点间会自然产生针对该 Egress IP 的 ARP 请求与应答。这些 ARP 交互会被物理交换机（`br-ocp`）学习，从而在其 MAC 地址表中建立 `192.168.66.100` 对应 MAC 和端口的映射。

#### 关键验证

**1. 上游路由器只能看到 ARP 广播请求，看不到应答**
```bash
# 在 FRR 路由器上抓包 —— 只有 ARP Request（广播），没有 Reply
[root@routing-frr ~]# tcpdump -i any -nnn host 192.168.66.100
# 19:42:10.039428 enp1s0 B   ARP, Request who-has 192.168.66.100 tell 192.168.99.24, length 28
# 19:43:02.354098 enp7s0 B   ARP, Request who-has 192.168.66.100 tell 192.168.99.25, length 28
# 19:43:04.502257 enp1s0 B   ARP, Request who-has 192.168.66.100 tell 192.168.99.23, length 28
# （只有广播 Request，没有任何 Reply）
```

**2. Egress IP 托管节点正确响应 ARP，且应答经物理网卡发出**
```bash
# 在 master-02（Egress IP 托管节点）上抓取所有接口
oc debug node/master-02-demo -- bash -c "tcpdump -i any -v -nnn 'arp and host 192.168.66.100' -c 10"
# 13:28:20.602372 enp2s0 B   ARP, Request who-has 192.168.66.100 tell 192.168.66.23, length 28
# 13:28:20.602934 br-ex  B   ARP, Request who-has 192.168.66.100 tell 192.168.66.23, length 28
# 13:28:20.602955 br-ex  Out ARP, Reply 192.168.66.100 is-at 00:50:56:8e:2a:32, length 28
# 13:28:20.603185 enp1s0 Out ARP, Reply 192.168.66.100 is-at 00:50:56:8e:2a:32, length 28
# ↑ Reply 从 br-ex 生成，经 enp1s0 物理网卡发出到物理网络
```

**3. 发起 ARP 的节点成功收到应答**
```bash
# 从 master-01 手动 arping —— 成功收到 master-02 的 MAC 地址
oc debug node/master-01-demo -- chroot /host bash -c "arping -c 3 -I br-ex 192.168.66.100"
# ARPING 192.168.66.100 from 192.168.66.23 br-ex
# Unicast reply from 192.168.66.100 [00:50:56:8E:2A:32]  2.148ms
# Unicast reply from 192.168.66.100 [00:50:56:8E:2A:32]  3.988ms
# Received 3 response(s)
```

#### 原因分析

| 帧类型 | 转发行为 | FRR 路由器可见性 |
|--------|---------|-----------------|
| ARP Request（广播） | 交换机泛洪到所有端口 | ✅ 可见 |
| ARP Reply（单播） | 交换机仅转发到目标 MAC 端口 | ❌ 不可见 |

#### 数据中心影响

物理交换机（`br-ocp`）通过 ARP Reply 的源 MAC 学习到 `00:50:56:8e:2a:32`（master-02）对应的端口映射。这意味着 Egress IP 实际上有**双重可达路径**：

- **L3 BGP 路由**（跨子网设备使用）：外部设备 → FRR 查 BGP 表 → 转发到 `192.168.99.24`
- **L2 ARP 直达**（同 L2 域设备使用）：同网段节点 → ARP 解析 → 直接 L2 转发到 master-02

BGP 的核心价值在于**跨 L3 边界的可达性和故障切换**，而非同 L2 域内的寻址。

## 8. 总结 (Conclusion)

OpenShift 4.19 中的 OVN Egress IP 方案通过将路由决策下沉到 OVS 与内核策略路由，实现了高性能、非集中式的出口控制。相较于传统模式，它通过直接操纵 OVS 寄存器实现“跨节点流量劫持”，在多网卡环境下表现尤为卓越。理解 BGP 的动态宣告与底层的十六进制 IP 映射逻辑，是调试现代云原生网络架构的关键钥匙。
