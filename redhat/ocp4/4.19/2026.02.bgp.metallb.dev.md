# Deep Dive: BGP Ingress Traffic Flow with MetalLB in OpenShift 4.19

## 概述 (Overview)

在 **OpenShift 4.19** 中，使用 **MetalLB** 配合 **FRR-K8s** 驱动可以实现基于 BGP 的服务发布（Ingress）。与 Egress Service 不同，Ingress 流量关注的是如何将外部流量通过 BGP 路由引入集群，并均匀地分配到后端的 Pod 上。本文档深入探讨了从 BGP 路由宣告、到宿主机 `iptables` 拦截、再到 OVN 逻辑流表转发的完整过程。

## 3. 流量处理深度追踪 (Traffic Deep Dive)

当一个外部包的目的地为 `192.168.66.100:8080` 到达集群节点时，其处理路径涉及宿主机 Iptables 和 OVN 的紧密协作。

### 3.1 第一步：宿主机 Iptables DNAT

在宿主机的 `nat` 表中，OVN-Kubernetes 设置了拦截规则，将到达 VIP 的流量重定向到 ClusterIP。

```bash
oc debug node/master-01-demo -- ip r
# default via 192.168.99.1 dev br-ex proto static
# 10.132.0.0/14 via 10.134.0.1 dev ovn-k8s-mp0
# 10.134.0.0/23 dev ovn-k8s-mp0 proto kernel scope link src 10.134.0.2
# 169.254.0.0/17 dev br-ex proto kernel scope link src 169.254.0.2
# 169.254.0.1 dev br-ex src 192.168.99.23
# 169.254.0.3 via 10.134.0.1 dev ovn-k8s-mp0
# 172.22.0.0/16 via 169.254.0.4 dev br-ex src 169.254.0.2 mtu 1400
# 192.168.66.0/24 dev br-ex proto kernel scope link src 192.168.66.23 metric 48
# 192.168.77.0/24 dev enp2s0 proto kernel scope link src 192.168.77.23 metric 100
# 192.168.99.0/24 dev br-ex proto kernel scope link src 192.168.99.23 metric 48


# 在 master-01-demo 节点查看 iptables
oc debug node/master-01-demo -- chroot /host bash -c 'iptables -t nat -S | grep 192.168.66.100'
# 输出：
# -A OVN-KUBE-EXTERNALIP -d 192.168.66.100/32 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.22.88.148:8080
```
- **证据证明**：外部流量在进入 OVN 逻辑网络之前，已经在主机层面被转换为 ClusterIP。

### 3.2 第二步：OVN Gateway Router (GR) 的 SNAT —— 入站流量的源地址伪装

DNAT 之后，流量的目标地址已变为 ClusterIP `172.22.88.148`。根据宿主机路由表：

```bash
# ClusterIP 路由指向 br-ex，最终进入 OVN Gateway Router (GR)
# 172.22.0.0/16 via 169.254.0.4 dev br-ex src 169.254.0.2 mtu 1400
```

流量通过 `br-ex` 进入 **GR_master-01-demo** 的外部端口 (`rtoe`)。此时，GR 承担了两个关键职责：**对 ClusterIP 进行二次 DNAT（负载均衡到 Pod IP）** 以及 **对源 IP 进行 SNAT（伪装为 Join IP）**。

#### 3.2.1 GR 端口信息

```bash
OVN_POD=$(oc get po -n openshift-ovn-kubernetes -l app=ovnkube-node -o wide | grep "master-01-demo" | awk '{print $1}')

# 查看 GR 端口列表
oc exec -n openshift-ovn-kubernetes $OVN_POD -c nbdb -- ovn-nbctl lrp-list GR_master-01-demo
# 528cab44-41ff-45cd-8b8b-beff3c38a828 (rtoe-GR_master-01-demo)
# 564e98d2-08a7-4eab-977f-886f128f95ae (rtoj-GR_master-01-demo)

# 查看 Join 端口 IP (这是 SNAT 的目标地址)
oc exec -n openshift-ovn-kubernetes $OVN_POD -c nbdb -- ovn-nbctl get logical_router_port rtoj-GR_master-01-demo networks mac
# ["100.64.0.4/16"]
# "0a:58:64:40:00:04"

# 查看 External 端口 IP
oc exec -n openshift-ovn-kubernetes $OVN_POD -c nbdb -- ovn-nbctl get logical_router_port rtoe-GR_master-01-demo networks mac
# ["192.168.99.23/24"]
# "00:50:56:8e:2a:31"
```

*   **`rtoe-GR_master-01-demo`**: 外部端口，IP `192.168.99.23/24`，连接物理网络。
*   **`rtoj-GR_master-01-demo`**: Join 端口，IP `100.64.0.4/16`，连接 OVN Join Switch，通往 `ovn_cluster_router`。

#### 3.2.2 GR 逻辑流表中的 DNAT + force_snat 标记

在 GR 的 `lr_in_dnat` (table=9) 流表中，可以直接找到针对 VIP `192.168.66.100` 的负载均衡规则：

```bash
oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-sbctl lflow-list GR_master-01-demo | grep -i snat | grep "192.168.66.100"
# 输出：
# table=9 (lr_in_dnat         ), priority=120  , match=(ct.new && !ct.rel && ip4 && ip4.dst == 192.168.66.100 && tcp && tcp.dst == 8080), action=(flags.force_snat_for_lb = 1; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080; force_snat);)
```

**关键动作解析**：
*   `flags.force_snat_for_lb = 1`：设置"强制 SNAT"标志位，告知后续 pipeline 必须执行 SNAT。
*   `ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080; force_snat)`：执行 conntrack 负载均衡，将 ClusterIP DNAT 到后端 Pod IP，同时在 CT Mark 中标记 `force_snat`。

#### 3.2.3 GR 逻辑流表中的 SNAT 执行 (lr_out_snat)

**这就是 SNAT 真正发生的位置！** 在 GR 的出站 SNAT pipeline `lr_out_snat` (table=3) 中：

```bash
oc exec -n openshift-ovn-kubernetes $OVN_POD -c ovn-controller -- ovn-sbctl lflow-list GR_master-01-demo | grep "lr_out_snat" | grep "force_snat_for_lb"
# 输出：
# table=3 (lr_out_snat        ), priority=110  , match=(flags.force_snat_for_lb == 1 && flags.network_id == 0 && ip4 && outport == "rtoe-GR_master-01-demo"), action=(ct_snat(192.168.99.23);)
# table=3 (lr_out_snat        ), priority=110  , match=(flags.force_snat_for_lb == 1 && flags.network_id == 0 && ip4 && outport == "rtoj-GR_master-01-demo"), action=(ct_snat(100.64.0.4);)
# table=3 (lr_out_snat        ), priority=105  , match=(flags.force_snat_for_lb == 1 && ip4 && outport == "rtoe-GR_master-01-demo"), action=(ct_snat(192.168.99.23);)
# table=3 (lr_out_snat        ), priority=105  , match=(flags.force_snat_for_lb == 1 && ip4 && outport == "rtoj-GR_master-01-demo"), action=(ct_snat(100.64.0.4);)
```

**核心证据解读**：

| 条件 | 出端口 | SNAT 目标 IP | 含义 |
|------|--------|-------------|------|
| `force_snat_for_lb == 1` | `rtoj` (Join 端口) | **`100.64.0.4`** | 流量发往跨节点 Pod 时，源 IP 伪装为 GR 的 Join IP |
| `force_snat_for_lb == 1` | `rtoe` (External 端口) | **`192.168.99.23`** | 流量回发到外部时，源 IP 伪装为节点 IP |

*   **当流量通过 `rtoj` 去往后端 Pod**（跨节点场景，Pod 在 master-02 或 master-03 上）：
    *   源 IP 从 **客户端真实 IP** → **`100.64.0.4`** (GR Join IP)
    *   这确保了后端 Pod 的**回包必须原路返回**到同一个 GR (`GR_master-01-demo`)，因为 `100.64.0.4` 是该 GR 在 Join Switch 上的专属地址。

#### 3.2.4 完整的入站数据包生命周期

```
外部客户端 (src: Client IP, dst: 192.168.66.100:8080)
        │
        ▼ [BGP ECMP 路由选择 master-01-demo]
┌─ 宿主机 master-01-demo ──────────────────────┐
│  ① iptables DNAT (nat/PREROUTING)             │
│     dst: 192.168.66.100 → 172.22.88.148       │
│                                                │
│  ② 路由查找: 172.22.0.0/16 via 169.254.0.4    │
│     → 流量进入 br-ex → OVN GR                  │
└────────────────────────────────────────────────┘
        │
        ▼
┌─ OVN GR_master-01-demo ──────────────────────┐
│  ③ lr_in_dnat (table=9):                      │
│     DNAT: 172.22.88.148 → Pod IP              │
│     设置: flags.force_snat_for_lb = 1         │
│                                                │
│  ④ lr_out_snat (table=3):                     │
│     SNAT: Client IP → 100.64.0.4 (Join IP)   │
│     出端口: rtoj → Join Switch                │
└────────────────────────────────────────────────┘
        │
        ▼
┌─ OVN ovn_cluster_router ─────────────────────┐
│  ⑤ 路由转发: 根据 Pod IP 子网选择目标节点      │
│     10.132.0.39 → master-02-demo 的 switch    │
│     10.133.0.4  → master-03-demo 的 switch    │
└────────────────────────────────────────────────┘
        │
        ▼
┌─ 目标节点 Logical Switch ────────────────────┐
│  ⑥ 数据包到达后端 Pod                         │
│     src: 100.64.0.4, dst: Pod IP              │
│                                                │
│  ⑦ 回包: Pod → 100.64.0.4 (GR Join IP)       │
│     → 原路返回 GR_master-01-demo              │
│     → GR 执行 reverse SNAT/DNAT (conntrack)  │
│     → 回包发回外部客户端                       │
└────────────────────────────────────────────────┘
```

> **结论**：SNAT 发生在 **OVN Gateway Router (GR) 的 `lr_out_snat` pipeline (table=3)** 中。当 `flags.force_snat_for_lb` 被 DNAT 阶段设置后，GR 在将流量从 join 端口 (`rtoj`) 发出时，将客户端源 IP 伪装为 **`100.64.0.4`** (GR 的 Join IP)。这确保了非对称路由场景下（入站节点 ≠ Pod 所在节点），回包能正确返回到原始入站 GR，最终送回外部客户端。

### 3.3 第三步：Logical Switch 层面的 LB 规则

除了 GR 层面的 DNAT + SNAT，OVN 南向数据库（Southbound DB）中在 Logical Switch 层面也预置了针对 ClusterIP 的 LB 规则。这些规则在流量从 `ovn-k8s-mp0` 进入（如本节点内部访问 ClusterIP）时生效：

```bash

oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovn-sbctl lflow-list | grep -E "172.22.88.148|192.168.66.100"
# 逻辑流表证据：

  # table=9 (lr_in_dnat         ), priority=120  , match=(ct.new && !ct.rel && ip4 && ip4.dst == 192.168.66.100 && tcp && tcp.dst == 8080), action=(flags.force_snat_for_lb = 1; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080; force_snat);)
  # table=6 (ls_in_pre_stateful ), priority=120  , match=(reg0[2] == 1 && ip4.dst == 192.168.66.100 && tcp.dst == 8080), action=(reg4 = 192.168.66.100; reg2[0..15] = 8080; ct_lb_mark;)
  # table=13(ls_in_lb           ), priority=120  , match=(ct.new && ip4.dst == 192.168.66.100 && tcp.dst == 8080), action=(reg4 = 192.168.66.100; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)
```

### 3.4 第四步：OVN 到 OVS 的流表翻译机制

`ovn-controller` 负责将上述逻辑流表下载（Translation）并转化为 OVS 的 `OpenFlow` 规则。

**核心逻辑：**
1.  **UUID 映射**：OVN 逻辑流表的每个条目都有一个唯一的 UUID。`ovn-controller` 会计算该 UUID 的哈希值，并将其作为 OVS 流表的 `cookie`。
2.  **Pipeline 转换**：OVN 的 Table ID 会映射到 OVS 的特定 Table。例如，LS 逻辑端口的入口表通常对应 OVS 的 Table 0 以后的逻辑。

```bash
# 1. 逆向查询：在 OVN 南向库中寻找对应的逻辑流表 (带 UUID 输出)
# 这里我们搜索 ClusterIP 172.22.88.148
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c sbdb -- ovn-sbctl --uuid lflow-list | grep -B 1 "172.22.88.148"
# 输出结果：
# uuid=0x93f7000b, table=13(ls_in_lb           ), priority=120  , match=(ct.new && ip4.dst == 172.22.88.148 && tcp.dst == 8080), action=(reg4 = 172.22.88.148; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)

# 2. 在物理节点通过 Cookie (即 UUID 的前 8 位) 定位 OVS 流表
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovs-ofctl dump-flows br-int | grep "cookie=0x93f7000b"
# 输出结果：
# cookie=0x93f7000b, duration=17039.689s, table=21, n_packets=0, n_bytes=0, idle_age=17039, priority=120,ct_state=+new+trk,tcp,metadata=0x2,nw_dst=172.22.88.148,tp_dst=8080 actions=load:0xac165894->NXM_NX_XXREG1[96..127],load:0x1f90->NXM_NX_XXREG0[32..47],group:133


oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovs-ofctl dump-groups br-int | grep "group_id=133"
#  group_id=133,type=select,selection_method=dp_hash,bucket=bucket_id:0,weight:100,actions=ct(commit,table=22,zone=NXM_NX_REG13[0..15],nat(dst=10.132.0.39:8080),exec(load:0x1->NXM_NX_CT_MARK[1])),bucket=bucket_id:1,weight:100,actions=ct(commit,table=22,zone=NXM_NX_REG13[0..15],nat(dst=10.133.0.4:8080),exec(load:0x1->NXM_NX_CT_MARK[1]))
```

#### 3.4.1 技术细节深度解析 (Deep Technical Analysis)

1.  **Cookie 与 UUID 的纽带**: 
    OVS 流表中的 `cookie=0x93f7000b` 正好对应 OVN Logical Flow 的 UUID `0x93f7000b`（截取前 8 位）。这种映射机制证明了 `ovn-controller` 在翻译流表时，将逻辑层的标识符持久化到了物理层的 `cookie` 中。这对于排查故障至关重要：通过物理流表的 cookie，我们可以直接回溯到 OVN 的 Logical Flow。

2.  **OVS 流表匹配解析 (Match Interpretation)**:
    *   `ct_state=+new+trk`: 这表示匹配一个新的、且已被 `conntrack` 状态机跟踪的连接。
    *   `nw_dst=172.22.88.148`, `tp_dst=8080`: 匹配目标 ClusterIP 和端口。由于流量在进入 OVN 前已由宿主机 `iptables` 执行了 DNAT，因此这里匹配的是转换后的内部地址。

3.  **动作执行与负载均衡 (Actions & Group)**:
    *   `group:133`: 流量被交给 OVS Group 133 处理。在 OVN 中，`ct_lb` 动作通常被翻译为 `type=select` 的 OVS Group，以利用 OpenFlow 的分发能力。
    *   `selection_method=dp_hash`: 在 Group 133 中，使用内核 `dp_hash` 算法根据五元组进行负载均衡。
    *   `nat(dst=10.132.0.39:8080)`: 这是物理层最后的执行动作，数据包在这里完成了从 ClusterIP 到后端 Pod IP 的转换。

4.  **UUID 的产生源头 (The Source of UUID)**:
    *   **NB 数据库**: 用户定义 Service 后，OVN-Kubernetes 在 Northbound DB (NBDB) 创建逻辑对象。
    *   **SB 数据库**: `ovn-northd` 监听到变化，将其翻译为 Southbound DB (SBDB) 中的 `Logical_Flow`。
    *   **UUID 生成**: 在 `ovn-northd` 插入 `Logical_Flow` 时，**OVSDB Server** 根据 RFC 4122 标准自动生成唯一的 `_uuid` 并持久化。
    *   **Cookie 映射**: 节点的 `ovn-controller` 同步该 `Logical_Flow`，并在下发物理流表时，截取 UUID 的前 32 位赋给 `cookie` 字段。

> **洞察 (In-depth)**：这种 `cookie` 关联机制是排查 OVN 网络故障的终极手段，通过 `ovn-sbctl` 找到 Logical Flow，进而定位到 `br-int` 真实的硬件驱动流表。

## 5. 结论 (Conclusion)

在 OpenShift 4.19 中，基于 MetalLB 的 BGP Ingress 方案通过 `iptables` 和 `OVN` 的多级协作实现了高效的流量引入：
1.  **BGP** 解决了流量如何被路由到物理节点的问题。
2.  **Iptables DNAT** 快速完成了 VIP 到 ClusterIP 的初步解映射。
3.  **OVN GR DNAT + SNAT** 在 Gateway Router 的 `lr_in_dnat` 中将 ClusterIP 负载均衡到后端 Pod IP，并在 `lr_out_snat` 中将客户端源 IP **SNAT 为 GR 的 Join IP**（如 `100.64.0.4`），确保跨节点场景下回包能正确返回原始入站 GR。
4.  **OVN Logical Switch LB** 在逻辑交换机层面提供了基于 OVS 状态跟踪的高性能服务发现和负载均衡。

这种架构避免了对单个入口节点的依赖，实现了真正的集群级入站流量分发。

### 关于 169.254.0.3 的深度调研

在 OVN-Kubernetes 中，`169.254.0.3` 是一个核心的**内部伪装 IP (Internal Masquerade IP)**，专门用于处理 `externalTrafficPolicy: Local` 的 Service。

#### 1. 流量入口：iptables DNAT
当外部流量到达 LoadBalancer VIP 时，主机 `iptables` 会将其 DNAT 到这个保留地址：
`-A OVN-KUBE-ETP -d 192.168.66.100/32 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 169.254.0.3:32736`

#### 2. 衔接点：主机路由
主机路由表将发往 `169.254.0.3` 的流量导向 OVN 管理端口 (`ovn-k8s-mp0`)，使其进入 OVN 逻辑网络：
`169.254.0.3 via 10.134.0.1 dev ovn-k8s-mp0`（10.134.0.1 为该节点的 OVN 网关地址）

#### 3. 核心分发：OVN Logical Load Balancer
进入 OVN 后，通过查询 OVN Northbound DB 可以发现，每个节点都有一个与之对应的 Logical Load Balancer，其中的 `169.254.0.3:32736` **仅包含本地 Pod 后端**：
