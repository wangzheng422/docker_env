# Deep Dive: BGP Ingress Traffic Flow with MetalLB in OpenShift 4.19

## 概述 (Overview)

在 **OpenShift 4.19** 中，使用 **MetalLB** 配合 **FRR-K8s** 驱动可以实现基于 BGP 的服务发布（Ingress）。与 Egress Service 不同，Ingress 流量关注的是如何将外部流量通过 BGP 路由引入集群，并均匀地分配到后端的 Pod 上。本文档深入探讨了从 BGP 路由宣告、到宿主机 `iptables` 拦截、再到 OVN 逻辑流表转发的完整过程。

---

本次验证在 3 节点的紧凑版集群上进行，所有节点均具有 `master` 和 `worker` 角色。

*   **节点 IP**: `192.168.99.23`, `192.168.99.24`, `192.168.99.25`
*   **服务负载均衡 IP (VIP)**: `192.168.66.100`
*   **ClusterIP**: `172.22.88.148`
*   **后端 Pod**:
    *   Pod 1: `10.132.0.39` (运行于 `master-02-demo`)
    *   Pod 2: `10.133.0.4` (运行于 `master-03-demo`)

## 2. 基础配置 (Infrastructure Configuration)

### 2.1 MetalLB 基础配置与 BGP 公告

除了地址池，我们还需要显式配置 `BGPPeer` 以建立与上游路由器的邻居关系。

```yaml
# BGPPeer 定义：建立 BGP 邻居关系
apiVersion: metallb.io/v1beta2
kind: BGPPeer
metadata:
  name: peer-sample1
  namespace: metallb-system
spec:
  peerAddress: 192.168.99.12
  peerASN: 64512
  myASN: 64512
  peerPort: 179

---
# IPAddressPool 定义
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: egress-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.66.100-192.168.66.100

---
# BGPAdvertisement 定义：选择所有 master 节点进行宣告
apiVersion: metallb.io/v1beta1
kind: BGPAdvertisement
metadata:
  name: egress-identity-bgp-adv
  namespace: metallb-system
spec:
  ipAddressPools:
  - egress-pool
  nodeSelectors:
  - matchLabels:
      node-role.kubernetes.io/master: ""
```

## 3. 流量处理深度追踪 (Traffic Deep Dive)

当一个外部包的目的地为 `192.168.66.100:8080` 到达集群节点时，其处理路径涉及宿主机 Iptables 和 OVN 的紧密协作。

### 3.1 第一步：宿主机 Iptables DNAT

在宿主机的 `nat` 表中，OVN-Kubernetes 设置了拦截规则，将到达 VIP 的流量重定向到 ClusterIP。

```bash
# 在 master-01-demo 节点查看 iptables
oc debug node/master-01-demo -- chroot /host bash -c 'iptables -t nat -S | grep 192.168.66.100'
# 输出：
# -A OVN-KUBE-EXTERNALIP -d 192.168.66.100/32 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.22.88.148:8080
```
- **证据证明**：外部流量在进入 OVN 逻辑网络之前，已经在主机层面被转换为 ClusterIP。

### 3.2 第二步：OVN 逻辑流表 (Logical Flow) 处理

流量经过 DNAT 后，目的地址变为 `172.22.88.148`。OVN 南向数据库（Southbound DB）中已经预置了针对该 ClusterIP 和 VIP 的 LB 规则。

```bash
# 查询 OVN Logical Flows
OVN_NODE_01_POD=$(oc get po -n openshift-ovn-kubernetes -l app=ovnkube-node -o wide | grep "master-01-demo" | awk '{print $1}')
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovn-sbctl lflow-list | grep -E "172.22.88.148|192.168.66.100"
# 逻辑流表证据：
  # table=7 (lr_in_defrag       ), priority=100  , match=(ip && ip4.dst == 172.22.88.148), action=(ct_dnat;)
  # table=7 (lr_in_defrag       ), priority=100  , match=(ip && ip4.dst == 192.168.66.100), action=(ct_dnat;)
  # table=9 (lr_in_dnat         ), priority=120  , match=(ct.new && !ct.rel && ip4 && ip4.dst == 172.22.88.148 && tcp && tcp.dst == 8080), action=(flags.force_snat_for_lb = 1; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080; force_snat);)
  # table=9 (lr_in_dnat         ), priority=120  , match=(ct.new && !ct.rel && ip4 && ip4.dst == 192.168.66.100 && tcp && tcp.dst == 8080), action=(flags.force_snat_for_lb = 1; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080; force_snat);)
  # table=6 (ls_in_pre_stateful ), priority=120  , match=(reg0[2] == 1 && ip4.dst == 172.22.88.148 && tcp.dst == 8080), action=(reg4 = 172.22.88.148; reg2[0..15] = 8080; ct_lb_mark;)
  # table=6 (ls_in_pre_stateful ), priority=120  , match=(reg0[2] == 1 && ip4.dst == 192.168.66.100 && tcp.dst == 8080), action=(reg4 = 192.168.66.100; reg2[0..15] = 8080; ct_lb_mark;)
  # table=13(ls_in_lb           ), priority=120  , match=(ct.new && ip4.dst == 172.22.88.148 && tcp.dst == 8080), action=(reg4 = 172.22.88.148; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)
  # table=13(ls_in_lb           ), priority=120  , match=(ct.new && ip4.dst == 192.168.66.100 && tcp.dst == 8080), action=(reg4 = 192.168.66.100; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)
```

### 3.3 第三步：OVN 到 OVS 的流表翻译机制

`ovn-controller` 负责将上述逻辑流表下载（Translation）并转化为 OVS 的 `OpenFlow` 规则。

**核心逻辑：**
1.  **UUID 映射**：OVN 逻辑流表的每个条目都有一个唯一的 UUID。`ovn-controller` 会计算该 UUID 的哈希值，并将其作为 OVS 流表的 `cookie`。
2.  **Pipeline 转换**：OVN 的 Table ID 会映射到 OVS 的特定 Table。例如，LS 逻辑端口的入口表通常对应 OVS 的 Table 0 以后的逻辑。

```bash
# 通过 OVN 逻辑流表的 UUID 哈希找到对应的 OVS 流表条目 (示例 cookie)
oc exec -n openshift-ovn-kubernetes $OVN_NODE_01_POD -c ovn-controller -- ovs-ofctl dump-flows br-int | grep "cookie=0xeff48f79"
# 输出摘要：
# table=13, cookie=0xeff48f79, priority=120,ct.new,ip,nw_dst=172.22.88.148,tp_dst=8080 actions=load:0xac165894->NXM_NX_REG4[],load:0x1f90->NXM_NX_REG2[0..15],ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080)
```
- **洞察 (In-depth)**：这种 `cookie` 关联机制是排查 OVN 网络故障的终极手段，通过 `ovn-sbctl` 找到 Logical Flow，进而定位到 `br-int` 真实的硬件驱动流表。

---

## 5. 结论 (Conclusion)

在 OpenShift 4.19 中，基于 MetalLB 的 BGP Ingress 方案通过 `iptables` 和 `OVN` 的两级协作实现了高效的流量引入：
1.  **BGP** 解决了流量如何被路由到物理节点的问题。
2.  **Iptables** 快速完成了 VIP 到 ClusterIP 的初步解映射。
3.  **OVN Logical Flows** 提供了基于 OVS 状态跟踪的高性能服务发现和负载均衡。

这种架构避免了对单个入口节点的依赖，实现了真正的集群级入站流量分发。
