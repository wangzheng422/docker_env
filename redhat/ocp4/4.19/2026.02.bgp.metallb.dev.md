# Deep Dive: BGP Ingress Traffic Flow with MetalLB in OpenShift 4.19

## 概述 (Overview)

在 **OpenShift 4.19** 中，使用 **MetalLB** 配合 **FRR-K8s** 驱动可以实现基于 BGP 的服务发布（Ingress）。与 Egress Service 不同，Ingress 流量关注的是如何将外部流量通过 BGP 路由引入集群，并均匀地分配到后端的 Pod 上。本文档深入探讨了从 BGP 路由宣告、到宿主机 `iptables` 拦截、再到 OVN 逻辑流表转发的完整过程。

---

## 1. 验证拓扑 (Validation Topology)

本次验证在 3 节点的紧凑版集群上进行，所有节点均具有 `master` 和 `worker` 角色。

*   **节点 IP**: `192.168.99.23`, `192.168.99.24`, `192.168.99.25`
*   **服务负载均衡 IP (VIP)**: `192.168.66.100`
*   **ClusterIP**: `172.22.88.148`
*   **后端 Pod**:
    *   Pod 1: `10.132.0.39` (运行于 `master-02-demo`)
    *   Pod 2: `10.133.0.4` (运行于 `master-03-demo`)

---

## 2. 基础配置 (Infrastructure Configuration)

### 2.1 MetalLB 地址池与 BGP 公告

我们配置 `BGPAdvertisement` 同步由所有 master 节点宣告该 VIP，以实现负载均衡。

```yaml
# IPAddressPool 定义
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: egress-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.66.100-192.168.66.100

---
# BGPAdvertisement 定义：选择所有 master 节点进行宣告
apiVersion: metallb.io/v1beta1
kind: BGPAdvertisement
metadata:
  name: egress-identity-bgp-adv
  namespace: metallb-system
spec:
  ipAddressPools:
  - egress-pool
  nodeSelectors:
  - matchLabels:
      node-role.kubernetes.io/master: ""
```

### 2.2 验证 BGP 状态

通过检查 `openshift-frr-k8s` 命名空间下的 `FRRConfiguration`，可以确认 3 个节点均已生成宣告前缀。

```bash
oc get FRRConfiguration -n openshift-frr-k8s -o yaml
# 关键输出摘要：
# prefixes:
# - 192.168.66.100/32
```

## 3. 流量处理深度追踪 (Traffic Deep Dive)

当一个外部包的目的地为 `192.168.66.100:8080` 到达集群节点时，其处理路径如下：

### 3.1 第一步：宿主机 Iptables DNAT

在宿主机的 `nat` 表中，OVN-Kubernetes 设置了拦截规则，将到达 VIP 的流量重定向到 ClusterIP。

```bash
# 在 master-01-demo 节点查看 iptables
iptables -t nat -S | grep 192.168.66.100
# 输出：
# -A OVN-KUBE-EXTERNALIP -d 192.168.66.100/32 -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.22.88.148:8080
```
- **证据证明**：外部流量在进入 OVN 逻辑网络之前，已经在主机层面被转换为 ClusterIP。

### 3.2 第二步：OVN 逻辑流表处理

流量经过 DNAT 后，目的地址变为 `172.22.88.148`。接下来，OVN 逻辑交换机（Logical Switch）接管流量并进行负载均衡。

通过查询 OVN 的 `Southbound DB`，我们可以看到 `ls_in_lb`（逻辑交换机入站负载均衡）阶段的处理：

```bash
# 查询 OVN Logical Flows
ovn-sbctl lflow-list | grep -A 2 "172.22.88.148"
# 逻辑流表证据：
# table=13(ls_in_lb), priority=120, 
# match=(ct.new && ip4.dst == 172.22.88.148 && tcp.dst == 8080), 
# action=(reg4 = 172.22.88.148; reg2[0..15] = 8080; ct_lb_mark(backends=10.132.0.39:8080,10.133.0.4:8080);)
```
- **核心逻辑**：
    1.  OVN 匹配 ClusterIP 目的地址。
    2.  `ct_lb_mark` 动作根据 L4 哈希选择后端 Pod IP（本例中为 `10.132.0.39` 或 `10.133.0.4`）。
    3.  此步骤完成了从 Service 到 Pod 的最终转发决策。

### 3.3 第三步：转发至目标 Pod

如果选中的后端 Pod 在当前节点，则直接交付；如果在其他节点，则通过 **Geneve** 隧道跨主机传输。

## 4. 连通性验证 (Connectivity Verification)

我们从 `master-01` 模拟外部请求访问 VIP：

```bash
# 从 master-01 (未运行业务 Pod 的节点) 访问 VIP
curl -s -I http://192.168.66.100:8080
# 输出：
# HTTP/1.0 200 OK
# Server: SimpleHTTP/0.6 Python/3.9.25
```

通过多次测试，可以看到流量被正确分发到运行于不同节点的后端 Pod。

---

## 5. 结论 (Conclusion)

在 OpenShift 4.19 中，基于 MetalLB 的 BGP Ingress 方案通过 `iptables` 和 `OVN` 的两级协作实现了高效的流量引入：
1.  **BGP** 解决了流量如何被路由到物理节点的问题。
2.  **Iptables** 快速完成了 VIP 到 ClusterIP 的初步解映射。
3.  **OVN Logical Flows** 提供了基于 OVS 状态跟踪的高性能服务发现和负载均衡。

这种架构避免了对单个入口节点的依赖，实现了真正的集群级入站流量分发。
