# 基于 BGP、OVN 与 Egress Service  方案 (OpenShift 4.19)


## 5. 实验环境搭建与验证过程

为进一步论证上述技术的有效性可行性，设计下列基于 Linux 原生虚拟机环境组网进行验证。此实验构建在一台高性能宿主机 Baremetal CentOS 9 操作系统的 KVM(libvirt) 平台上。宿主机的 `br-ocp` 网桥网段为 `192.168.99.0/24`（宿主机 IP 为 192.168.99.1）。

### 5.1 环境说明
1. **OpenShift 4.19 虚拟集群**: 配置 3 个虚机节点（compact 融合节点作为 Worker及Master），网卡挂载在 `br-ocp`。启用了 OVN-Kubernetes 默认 CNI，并加装具备 MetalLB 的扩展。
   - 节点 IP 处于：`192.168.99.23 ~ 192.168.99.25`
   - **分配的池化 Egress IP 网段**: `192.168.66.100/24`
2. **KVM Router 节点 (CentOS 9)**: 作为模拟数据中心骨干交换机，其上运行软件态 FRR 处理 BGP。
   - 对 OCP 侧连接的桥接桥 `eth0` (处于 br-ocp): `192.168.99.12`
   - 对 Server 端外网模拟口 `eth1`: `192.168.55.12` 
3. **KVM Server 节点 (CentOS 9)**: 充当外域业务服务器供校验 SNAT。
   - 网卡 `eth0` (连接 Router 的 eth1 侧): `192.168.55.13`，默认网关指向 `192.168.55.1`

### 5.2 Router (FRR) 节点配置与就绪
登入作为 Router 的 CentOS 9 虚机节点，首先需开启服务器的数据包内核转发，再进行 FRR 的策略搭建使得 BGP 监听来自各方集群 OCP Worker 的通告。

```bash
# 1. 安装基础路由组件
sudo dnf install -y frr

# 在启动之前，必须在 daemons 文件中显式启用 bgpd 进程
sudo sed -i 's/^bgpd=no/bgpd=yes/' /etc/frr/daemons

sudo systemctl enable --now frr

# 2. 开启内核 IPv4 转发能力
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.d/99-ipforward.conf
sudo sysctl -p /etc/sysctl.d/99-ipforward.conf

# 3. 编排 FRR 核心配置文件
cat <<EOF | sudo tee /etc/frr/frr.conf
frr defaults traditional
log syslog informational
no ipv6 forwarding
!
router bgp 64512
 bgp router-id 192.168.99.12
 
 ! 配置分别对接 OCP 集群内各节点的 iBGP 邻居
 neighbor 192.168.99.23 remote-as 64512
 neighbor 192.168.99.24 remote-as 64512
 neighbor 192.168.99.25 remote-as 64512

 ! 确保 iBGP 等价多路径 (ECMP) 与网络宣发在 address-family 内配置
 address-family ipv4 unicast
  network 192.168.55.0/24
  maximum-paths ibgp 4
 exit-address-family
!
line vty
!
EOF

# 4. 重载使路由生效
sudo systemctl restart frr
```

### 4.1. FRR-K8s (BGP) 基础配置
向外部核心交换机宣示 AS 以及邻居构建逻辑。
```yaml
apiVersion: frrk8s.metallb.io/v1beta1
kind: FRRConfiguration
metadata:
  name: bgp-core-router
  namespace: openshift-frr-k8s
  # labels:
  #   use-for-advertisements: 'true'  # 供 OVN-K 路由发布使用
spec:
  bgp:
    bfdProfiles:
      - name: fast-bfd
        detectMultiplier: 3  # 检测倍数：连续 3 次未收到报文则判定链路故障
    routers:
    - asn: 64512 # OCP 集群私有 AS 号
      neighbors:
      - address: 192.168.99.12 # 物理路由器(FRR VM)邻居 IP
        asn: 64512
        disableMP: true  # 必须设为 true（IPv4/IPv6 单独建会话）
        bfdProfile: fast-bfd  # 使用上面定义的 BFD 配置文件
        toAdvertise:
          allowed:
            mode: all
        toReceive:
          allowed:
            mode: filtered # 开启过滤模式
            prefixes:
            - prefix: 192.168.55.0/24 # 【白名单】只收这一条
      # prefixes:
      # - 192.168.66.100/32  # 必须显式允许此前缀发往外部路由器
```

### 5.5 EgressService 流量截留与 SNAT 原理深度验证

在 OpenShift 4.14+ (极度确认 4.19 也是如此) 的全新 OVN-Kubernetes 架构中，EgressService 已经 **完全抛弃了 OVN NBDB Router 的逻辑路由和 iptables 的 MASQUERADE 机制**。取而代之的是，它深嵌于 OVS OpenFlow 底层寄存器改写，并使用 Linux 原生的 **nftables 动态 Map** 来实现极致的 SNAT 转换。

按照以下步骤，您可以亲眼目睹这一奇迹的发生：

#### 1. 案发现场 1：源端 Pod 所在节点 (master-03) 的 OVS 暴力拦截
在源节点 `master-03` 上，当其上的 Pod (`10.133.0.3`) 发出的数据包刚进入底层的虚拟交换机 `br-int` 时，它直接撞上了这条优先级极高的 OVS 流表：

```bash
# 获取源节点上的 OVN 容器名
OVN_NODE_03_POD=$(oc get po -n openshift-ovn-kubernetes -l app=ovnkube-node -o wide | grep "master-03-demo" | awk '{print $1}')
# 拦截查询：看看是谁把包引向了隧道
oc exec -n openshift-ovn-kubernetes $OVN_NODE_03_POD -c ovn-controller -- ovs-ofctl dump-flows br-int | grep "10.133.0.3"
```

您将看到类似以下的铁证（Table 25）：
```text
cookie=0xb59ecc61, table=25, priority=101, ip, nw_src=10.133.0.3 
actions=load:0x64580004->NXM_NX_XXREG0[96..127],load:0x64580002->NXM_NX_XXREG1[64..95],mod_dl_src:0a:58:64:58:00:02, resubmit(,26)
```
**解读**：OVS 认出这是 Egress Service 劫持的对象，直接通过底层芯片级别的 `load` 指令（修改 XXREG 寄存器）篡改包的投递终点，并**修改 MAC 地址**。它剥夺了从 `master-03` 原生网关出网的权利，将其强行塞入外层 UDP 端口为 6081 的 **Geneve 隧道**，砸向了承载 Egress 的宿主节点 `master-01`。

#### 2. 案发现场 2：在宿主节点 (master-01) 亲眼目睹“变身”
我们可以通过原生的 `tcpdump` 工具（免 chroot）在 `master-01-demo` 的主机网络栈内，亲眼看见包从网络隧道中出来，并在出 `br-ex` 物理接口的关键时刻发生伪装。

准备两个控制台窗口：

**终端 1 (在 master-01 监听流量):**
```bash
oc debug node/master-01-demo -- bash -c "tcpdump -i any -n 'host 192.168.55.13' 2>/dev/null"
```

**终端 2 (在 master-03 的 Pod 内发包):**

```text
# 包从 Geneve 隧道剥离，以原生 10.133.0.3 进入主机网络栈（ovn-k8s-mp0）
13:28:40.907255 ovn-k8s-mp0 In  IP 10.133.0.3 > 192.168.55.13: ICMP echo request, id 4, seq 1, length 64

13:28:40.907295 br-ex Out IP 192.168.66.100 > 192.168.55.13: ICMP echo request, id 4, seq 1, length 64
```

#### 3. 终极真相：是谁下发的这道 SNAT 密令？
既然 OVN 的 NBDB Logical Router 里没有策略，那转换一定是发生在这毫秒级的内核传递间。它既不在普通的 `iptables -t nat`，也不在 `OVS CT`，它藏在 Linux 原生的 **nftables 动态映射表（Map）**中！

由于 OCP 的 debug 镜像没有预装 `nft`，我们必须 `chroot /host` 使用系统级的命令才能将其揭露：

```bash
# 提取 master-01 宿主机上由 OVN-K 动态写入的 nftables 路由图表
oc debug node/master-01-demo -- chroot /host /bin/bash -c "nft list ruleset | grep 'egress-service-snat-v4' -A 5 -B 5"
```

**最终的答案水落石出：**
```text
        map egress-service-snat-v4 {
                type ipv4_addr : ipv4_addr
                # 看这里！OVN 自动将 demo-egress 命名空间下的两个 Pod 的真实 IP，硬编码映射成了 Egress IP！
                elements = { 10.132.0.13 comment "demo-egress/egress-identity" : 192.168.66.100, 10.133.0.3 comment "demo-egress/egress-identity" : 192.168.66.100 }
        }

        chain egress-services {
                type nat hook postrouting priority srcnat; policy accept;
                # 执行无情替换：查表 @egress-service-snat-v4，命中即刻 SNAT 转换！
                snat ip to ip saddr map @egress-service-snat-v4
        }
```
至此破案：**`EgressService` 依托源节点 `OVS XXREG0/XXREG1` 寄存器重写引导流量入隧道，最后配合目标宿主机原生的底层 `nftables Map` 实现了零感知的源地址劫持出海。**
