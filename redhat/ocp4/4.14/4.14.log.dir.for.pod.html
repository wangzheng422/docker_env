persistent log for pod with multiple log files

Customer wants to use k8s/container platform/openshift, just as vm platform. They want to have a persistent log directory for each pod, and the log files should be kept after the pod is deleted. But k8s by default, only support STDOUT, STDERR for log, and the log files will be deleted after the pod is deleted.

The key problem here is that container only support 2 log streams, but app, like java app, may have multiple log files, and the log files are generated by the app itself, like gc.log, access.log, and so on. So, we need to find a way to keep the log files.

For customer moving from vm to container, they are familiar with file based log collecting system, like fluend, and most of them already have deploy such platform. So we will create a solution, that can work with the existing log collecting system. This means, we will write log to local file system, and the log files will be collected by the log collecting system.

using hostpath with retain policy

We will create log storage with hostpath provisioner, and use retain policy for the storage, so the log files will be kept after the pod is deleted. And we will create a demo app, that can write log to the log storage.

storage prepare

install cnv, and config a hostpath. We know the hostpath works for worker node, but it not work for master node.

apiVersion: hostpathprovisioner.kubevirt.io/v1beta1
kind: HostPathProvisioner
metadata:
  name: hostpath-provisioner
spec:
  imagePullPolicy: IfNotPresent
  storagePools:
    - name: local
      path: /var/wzh-local-log
  workload:
    nodeSelector:
      kubernetes.io/os: linux

then define a storage class

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-log-hostpath-csi
provisioner: kubevirt.io.hostpath-provisioner
reclaimPolicy: Retain 
volumeBindingMode: WaitForFirstConsumer 
parameters:
  storagePool: local

clean up pv

After pod exits, the PV used for log is in release status, this is because the reclaim policy is set to retain, we need to manually mark the PV to delete.


oc get pv | grep local-log-hostpath-csi | grep Released | awk '{print $1}' | \
  xargs -I {} oc patch pv {} -p '{"spec":{"persistentVolumeReclaimPolicy":"Delete"}}'

limitation & recommand

  1. enough space on local disk, especially the /var
  2. additional disk partition for /var/wzh-local-log
  3. consider using pv/pvc for storagePools

collect raw data files

For java heap dump, it is binary raw data, and log collect tools like fluentd, will not work with it, as it depends on tail and parser on the log file. We need to use other tools to collect the raw data files.

What we plan to do, is just create additional container, mount the bin data dir in RO mode, monitor the dir for bin data file changed and upload the file to remote sftp server.

In the bin-log collecting script, we use sftp command to upload file, and we use inotifywait to monitor the file changes. We expect there is sftp server running, and we can use sftp command to upload file to it, the sftp server should be enhanced with security, only allow upload, not download, and no ssh shell provided. Here is a sftp pod demo, for your reference.

cat << 'EOF' > ${BASE_DIR}/data/install/log-collect.sh
#!/bin/bash

# Define the local directory to monitor and the remote server directory
LOCAL_DIR="$ENV_LOCAL_DIR"
REMOTE_DIR="$ENV_REMOTE_DIR"

# Get the SFTP username and password from environment variables
SFTP_USER="$ENV_SFTP_USER"
SFTP_PASSWORD="$ENV_SFTP_PASSWORD"
SFTP_HOST="$ENV_SFTP_HOST" # Replace with your actual remote server host


# Create a temporary batch file to check and create the remote directory
INIT_BATCH_FILE=$(mktemp)
echo "mkdir $REMOTE_DIR" > $INIT_BATCH_FILE

# Use sshpass with sftp to automatically login and execute the batch file to ensure the remote directory exists
sshpass -p "$SFTP_PASSWORD" sftp -oBatchMode=no -b $INIT_BATCH_FILE -o StrictHostKeyChecking=no -oUserKnownHostsFile=/tmp/known_hosts $SFTP_USER@$SFTP_HOST

# Remove the temporary batch file for directory initialization
rm $INIT_BATCH_FILE

# Loop indefinitely
while true; do
  # Use inotifywait to monitor the directory for any change events and read the output
  inotifywait -e close_write --format '%w%f' $LOCAL_DIR | while read FILE; do
    # Check if the file exists before attempting to sync, as it might have been deleted
    if [ -e "$FILE" ]; then
      # Create a temporary batch file for sftp commands
      BATCH_FILE=$(mktemp)
      echo "put $FILE $REMOTE_DIR" > $BATCH_FILE
      
      # Use sshpass with sftp to automatically login using the provided username and password
      # and execute the batch file
      sshpass -p"$SFTP_PASSWORD" sftp -oBatchMode=no -b $BATCH_FILE -o StrictHostKeyChecking=no -oUserKnownHostsFile=/tmp/known_hosts $SFTP_USER@$SFTP_HOST

      # can also use scp
      # and use -l limit
      #       Limits the used bandwidth, specified in Kbit/s.
      # sshpass -p"$SFTP_PASSWORD" scp -o StrictHostKeyChecking=no -oUserKnownHostsFile=/tmp/known_hosts $FILE $SFTP_USER@$SFTP_HOST:$REMOTE_DIR/
      
      # Remove the temporary batch file
      rm $BATCH_FILE
    fi
  done
done
EOF

trigger java heap dump based on pod memory usage

Customer also needs an automatically way, to trigger the java heap dump, when the java app run out of the pod memory. We will use liveness pod of the container, and run a script to check the memory usage, and trigger the java heap dump.

It is better to use promethus and alertmanager to monitor the memory usage, and trigger the java heap dump, but our requirements is the solution should be as simple as possible, do not involve in other system components, so we will use liveness check to do the job.

If you have multiple liveness check logic, you have to combine them into one script.

token service to control concurrency

Customer has a limited backend network infrastructure, so the solution should have as little impact on the network infrastruct as possible. That means the total network bandwidth needed of this solution should be as low as possible. We will use a token service to control the concurrency of the java heap dump upload, so that only one java heap dump upload can be triggered at a time. And each of the upload session network speed will be limited.

We also need a solution to limit the upload only once for a container, which means the upload will switch to off automatically after the upload is done. And we also needs a way to reset the upload switch, so that the upload can be triggered again.

So in summary, the key requirements are:

  1. limit concurrency of upload session: to limite the overall network bandwidth usage, we need to control the upload session concurrency. With limit each upload session network speed, we can control the overall network bandwidth usage.
  2. one java heap dump for each container: We only needs the initial java heap dump when memory consumption over the limit, other java heap dump happened after the initial dump, does not meanful.
  3. (optional) limit concurrency of java heap dump: we find out that the java heap dump consume many local disk space, so we need a way to control the java heap dump concurrency, to avoid the local storage over usage issue.
  4. (optional) switch-on the java heap dump: after the switch is turned off, we need a centrol method to turn on the switch, so that the java heap dump can be triggered again.

There are several ways to achive the above requirements, each have their own pros and cons. Here are some possible solutions:

no. solution pros cons
1 local switch file for req 2 only, very simple and straiforward, but can not remote switch status back. for req 1, 3, other solutoin needed.
2 sftp server with max session configured for req 1 only, very simple and straiforward, clients just retry to upload for req 2, 3, other solution needed. And the same sftp server is not suitable with other purpose, like switch file.
3 sftp server with tc (traffic control) Controlling overall network bandwidth is very easy.
on host os, using tc
on k8s, using annotation “kubernetes.io/ingress-bandwidth”		 tc (traffic control) operate with priviledge. Limit the upload server selection
4 sftp server’s file system For req1, 3, can simulate a global lock to control the concurrency, but not accuracy.
For req 2, 4, can simulate centrol switch file for each container, and switch back on the centrol server.		 for req 1, 3, under race condition, concurrency control will not work as intend to do.
5 DIY token service for req 1, 3, client needs to get token from token service before operation.
For req 2, can be enhanced to work with promethuse’s alert rule.		 This DIY service is a small software project, and bring unkown risks to app deployment, for example, in rare condition, pod restarts, and leave dump files in local disk without release token, and other uploads session needs to wait token timeout.
For req 2, other solution needs, or complex token service needs to be developed.
6 DIY upload server/service merge external depency of sftp server and token service into single external service. This DIY is a relative larger software project, not suitable for a simple solution.

In this demo, we choose option 4 & 5, because it is more general purpose, and can be used in other scenarios.

To implement global concurrency control, a global concurrency control service is necessary, which includes a global lock and counter. Here are some possible solutions:

  1. Simulate the concurrency control using the sftp file system, optionally with setting max session on sftp server. However, this approach is not rigorous and cannot handle high concurrency scenarios effectively. For instance, if multiple memory dumps and upload requests occur simultaneously, concurrency control becomes challenging.
  2. Implement a custom solution using pure Python, utilizing Python’s built-in locks and counters. This approach offers flexibility and is suitable for systems with simple deployment architectures and a small number of concurrent locks.
  3. Develop a custom solution using Python based on Redis, leveraging Redis’s locks and counters. This approach is more robust and suitable for complex deployment structures and scenarios requiring the management of a large number of concurrent locks and complex locking logic.

For our demo, we selec the option 2, pure Python with Python build-in lock and counter.

# we will check local *.hprof file, if it exists, do not trigger heap dump

# Set the memory threshold to trigger a heap dump

# Get the total memory limit from the cgroup
TOTAL_MEMORY=$(cat /sys/fs/cgroup/memory/memory.limit_in_bytes)

# Calculate the threshold in bytes
THRESHOLD_BYTES=$((TOTAL_MEMORY * MEMORY_THRESHOLD / 100))

# Get the current memory usage
CURRENT_MEMORY=$(cat /sys/fs/cgroup/memory/memory.usage_in_bytes)

# before trigger heap dump, we will check the switch file on sftp server
# if there is switch file, we will not trigger heap dump
# if not, we will create the switch file, and then trigger heap dump
# we use switch file on remote sftp server instead of local fs
# so that we can re-enable memory dump by removing the switch file on the remote sftp server
check_switch_file() {

  # check the sftp switch file, if the file exists, do not trigger heap dump
  # Create a temporary batch file to check and create the remote directory
  INIT_BATCH_FILE=$(mktemp)
  echo "ls $REMOTE_DIR/upload.switch" > $INIT_BATCH_FILE

  # Execute the batch file with sftp
  if sshpass -p "$SFTP_PASSWORD" sftp -oBatchMode=no -b $INIT_BATCH_FILE -o StrictHostKeyChecking=no -oUserKnownHostsFile=/dev/null $SFTP_USER@$SFTP_HOST; then
    echo "Memory dump switch file exists."
    # that means switch off, do not trigger heap dump
    rm -f "$INIT_BATCH_FILE"

    return 0
  else
    echo "File does not exist."
    rm -f "$INIT_BATCH_FILE"

    return 1
  fi

}

  sshpass -p "$SFTP_PASSWORD" sftp -oBatchMode=no -b $INIT_BATCH_FILE -o StrictHostKeyChecking=no -oUserKnownHostsFile=/dev/null $SFTP_USER@$SFTP_HOST

  # create the switch file, so no further heap dump can be trigger
  touch /tmp/empty
  echo "$POD_NAMESPACE:$POD_NAME" > /tmp/empty
  echo "put /tmp/empty $REMOTE_DIR/upload.switch" > $INIT_BATCH_FILE
  if sshpass -p "$SFTP_PASSWORD" sftp -oBatchMode=no -b $INIT_BATCH_FILE -o StrictHostKeyChecking=no -oUserKnownHostsFile=/dev/null $SFTP_USER@$SFTP_HOST; then
    echo "Success to create switch file."
    rm -f "$INIT_BATCH_FILE" /tmp/empty
    return 0
  else
    echo "Failed to create switch file."
    rm -f "$INIT_BATCH_FILE" /tmp/empty
    return 1
  fi
}

# get the memory dump token from token service
get_global_token () {
  local token_service=$1
  local pod_name=$2
  local pod_namespace=$3

  # Create a temporary batch file for sftp commands
  BATCH_FILE=$(mktemp)

  # Call the token service to get a token
  encoded_value=$(jq -nr --arg pod_name "$pod_name" --arg namespace "$pod_namespace" '($namespace + ":" + $pod_name) | @uri')
  echo "Encoded value: $encoded_value"

  # Use -o to redirect the output to /dev/null (if the response body is not needed)
  # Use -w to write out the HTTP status code
  http_status=$(curl -s -o $BATCH_FILE -w "%{http_code}" -H "X-API-PASSWORD: your_password_here" "http://$token_service/issue_token?info=$encoded_value")

  echo "TOKEN_SERVICE: $token_service"
  echo "HTTP status: $http_status"

  echo "content of token service result:"
  cat $BATCH_FILE

  rm -f $BATCH_FILE

  # Check if the token retrieval was successful
  if [[ $http_status -eq 200 ]]; then
      echo "Token retrieved successfully. $token_service"
      return 0
  else
      echo "Failed to retrieve token. $token_service"
      return 1
  fi
}

# release the token after the memory dump is uploaded
release_global_token () {
  local token_service=$1
  local pod_name=$2
  local pod_namespace=$3

  # Call the token service to get a token
  encoded_value=$(jq -nr --arg pod_name "$pod_name" --arg namespace "$pod_namespace" '($namespace + ":" + $pod_name) | @uri')
  echo "Encoded value: $encoded_value"

  # and release the token
  curl -s -H "X-API-PASSWORD: your_password_here" "http://$token_service/recycle_token?info=$encoded_value"

  echo 'token released. $token_service'
}

trigger java heap dump using promethus alert

In the aforementioned solution, the liveness check includes memory usage checks. However, liveness checks are not suitable for this kind of logic. Firstly, both memory usage checks and script logic checks, such as token checks, consume time within the liveness check. If system jitters occur, liveness check failures might trigger pod restarts. Secondly, the liveness check interval remains fixed after pod deployment, making it unsuitable for flexible adjustments.

A more practical approach involves utilizing Prometheus alerts to trigger Java heap dumps. This allows better control over trigger conditions and frequencies. In the following demo, we’ll demonstrate leveraging OpenShift’s built-in Prometheus alert functionality to monitor Java pod memory usage. This will subsequently send an alert event to our webhook, which then calls the Java pod’s REST API to trigger a heap dump.

After integrating Prometheus alerts, the system architecture transforms as illustrated. Notably, the webhook effectively replaces the previous liveness check functionality. Moreover, we can potentially consolidate the token service within the webhook in the future, creating a unified service.

In this demo, the webhook integration is not comprehensive. We only showcased how to fetch alert events, obtain pod IP addresses from the events using pod names, and display the content of a sample alert event. The complete implementation of the webhook, including the queue, token service, switch service, and other components, should be tailored to specific project requirements.

  • groupInterval
    • How long to wait before sending an updated notification
  • repeatInterval
    • How long to wait before repeating the last notification
    groupInterval: 1m
    groupWait: 30s
    repeatInterval: 2m

We care about the groupWait, because we want the alert event to be sent as soon as possible after the alert is triggered. And after the dump is triggered, the pod can be killed.

So the total time after a memory occupation condition matching, and before the alert event is sent out is about 2m. 30s for prometheus to poll the value, 1m for prometheus to trigger the alert, 30s for alert manager to group and wait to send out the initial notification.

[!NOTE] Following an alert event, several time-consuming tasks arise in the subsequent process, including obtaining a heap dump token.

comparing different event trigger solution

We have 2 trigger solutions, one is prometheus alert, another is scripting in k8s liveness check. Lets compare them here.

no. solution pros cons
1 scripts in k8s liviness check The simplest architecture solution. Check logic freedom and ability to precisely control the maximum time interval between fault occurrence and heap dump triggering. The liveness check script should not be complex. If the script fails due to unexpected reasons such as large script size or complex logic, the container will be killed by k8s/ocp. Additionally, liveness check should be used for application monitoring and not for application performance monitoring.
2 prometheus alert manager OCP’s built-in monitoring and alerting features, combined with web hooks, provide a standard and common solution for monitoring and event response. The solution relies on more components within OCP, and from the occurrence of a fault to the sending of an alert message, it goes through several stages, making the calculation of the final time interval complex. Moreover, the business logic included in the solution has not changed, it is just repackaged into a web hooker, making the overall architecture more reasonable.
