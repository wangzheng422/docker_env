# KVM 网络性能调优方案

## 概述

本文档记录了在 AWS c5n.metal 实例上，通过一系列宿主机、虚拟机 XML 配置和 Guest OS 调优手段，使 KVM 虚拟机网络性能接近物理机水平的完整方案。

**关键约束**：AWS 环境不支持 SR-IOV / macvtap 网卡直通，所有优化基于 virtio-net + NAT 桥接模式。

---

## 调优效果总结

### iperf3 网络性能

| 测试场景 | 单流带宽 | 多流 P=16 带宽 |
|----------|----------|----------------|
| ec2A 物理机 → ec2B | 4.94 Gbits/sec | 23.1 Gbits/sec |
| KVM Guest 基线 → ec2B | 4.76 Gbits/sec (96.4%) | 9.24 Gbits/sec (40.0%) |
| **KVM Guest 优化后 → ec2B** | **4.94 Gbits/sec (100%)** | **13.4 Gbits/sec (58.0%)** |

- 单流性能：从 96.4% 提升到 **100%**，完全消除虚拟化开销
- 多流性能：从 40.0% 提升到 **58.0%**，提升 45%

### fio 磁盘性能

优化前后 fio 性能无退化（4k randread/randwrite 均在误差范围内），说明调优仅影响网络路径，不影响磁盘 I/O。

## 调优方案详解

### 一、宿主机内核模块

#### 1. 加载 vhost-net 模块

```bash
sudo modprobe vhost_net
echo "vhost_net" | sudo tee /etc/modules-load.d/vhost-net.conf
```

**原理**：vhost-net 将 virtio-net 的数据包处理从 QEMU 用户态进程移到内核态 vhost 工作线程，避免了用户态/内核态上下文切换开销。这是 KVM 网络性能优化的最基础也是最重要的一步。

**效果**：单独启用可提升 20-30% 的网络吞吐量。

#### 2. 加载并禁用 bridge netfilter

```bash
sudo modprobe br_netfilter
echo 0 | sudo tee /proc/sys/net/bridge/bridge-nf-call-iptables
echo 0 | sudo tee /proc/sys/net/bridge/bridge-nf-call-ip6tables
echo 0 | sudo tee /proc/sys/net/bridge/bridge-nf-call-arptables
```

持久化配置：
```bash
cat << EOF | sudo tee /etc/sysctl.d/99-bridge-nf.conf
net.bridge.bridge-nf-call-iptables = 0
net.bridge.bridge-nf-call-ip6tables = 0
net.bridge.bridge-nf-call-arptables = 0
EOF
```

**原理**：默认情况下，Linux 桥接会将所有经过网桥的数据包送入 iptables/ip6tables/arptables 进行过滤，这对于 KVM NAT 场景是不必要的开销。禁用后数据包直接转发，减少 CPU 周期消耗。

### 二、宿主机内存优化

#### 3. 大页内存 (Hugepages)

```bash
# 分配 8192 × 2MB = 16GB 大页（需大于 VM 内存 8GB）
echo 8192 | sudo tee /proc/sys/vm/nr_hugepages
```

持久化配置：
```bash
echo "vm.nr_hugepages = 8192" | sudo tee /etc/sysctl.d/99-hugepages.conf
```

**原理**：使用 2MB 大页替代默认 4KB 页面，将 TLB（页表缓存）miss 率降低数百倍。对于内存密集型的网络数据包处理，减少页表查找开销可显著提升性能。

**VM XML 配置**：
```xml
<memoryBacking>
  <hugepages/>
</memoryBacking>
```

### 三、VM XML 配置优化

#### 4. CPU 绑定 (vcpupin)

```xml
<vcpu placement='static'>8</vcpu>
<cputune>
  <vcpupin vcpu='0' cpuset='0'/>
  <vcpupin vcpu='1' cpuset='1'/>
  <vcpupin vcpu='2' cpuset='2'/>
  <vcpupin vcpu='3' cpuset='3'/>
  <vcpupin vcpu='4' cpuset='4'/>
  <vcpupin vcpu='5' cpuset='5'/>
  <vcpupin vcpu='6' cpuset='6'/>
  <vcpupin vcpu='7' cpuset='7'/>
  <emulatorpin cpuset='8-9'/>
</cputune>
```

**原理**：
- `vcpupin`：将虚拟 CPU 固定绑定到物理 CPU 核心，避免 vCPU 在物理核心间迁移导致的 L1/L2 缓存失效
- `emulatorpin`：将 QEMU emulator 线程绑定到独立的物理核心（8-9），避免 emulator 线程与 vCPU 争抢 CPU 资源
- 对多流网络测试影响最大，因为多个网络处理线程可以并行执行而不互相干扰

#### 5. CPU host-passthrough 模式

```xml
<cpu mode='host-passthrough' check='none'>
  <topology sockets='1' dies='1' cores='8' threads='1'/>
</cpu>
```

**原理**：
- `host-passthrough`：将宿主机 CPU 的所有特性（SSE4.2, AVX2, AES-NI 等）直接暴露给 Guest，避免 CPU 指令模拟开销
- 明确的 CPU 拓扑定义（1 socket × 8 cores）让 Guest 内核能正确识别 NUMA 拓扑，优化内存访问和中断分配

#### 6. Q35 机型

```xml
<os>
  <type arch='x86_64' machine='pc-q35-rhel9.4.0'>hvm</type>
</os>
```

**原理**：Q35 是现代 PCIe 架构的虚拟芯片组，相比传统 i440fx：
- 支持原生 PCIe 总线，virtio 设备作为 PCIe 设备呈现，减少总线模拟开销
- 更高效的中断路由（MSI-X）
- 更好的 IOMMU 支持

#### 7. virtio-net 多队列 + vhost 驱动

```xml
<interface type='network'>
  <source network='default'/>
  <model type='virtio'/>
  <driver name='vhost' queues='8'/>
</interface>
```

**原理**：
- `name='vhost'`：在 XML 层面指定使用 vhost-net 内核驱动处理网络 I/O
- `queues='8'`：启用多队列 virtio-net，允许多个 CPU 核心同时处理网络收发队列
- 多队列是提升多流网络性能的关键，单队列时所有网络中断只能被一个 CPU 处理

#### 8. 磁盘 I/O 优化

```xml
<disk type='block' device='disk'>
  <driver name='qemu' type='raw' cache='none' io='native'/>
  <source dev='/dev/nvme1n1'/>
  <target dev='vda' bus='virtio'/>
</disk>
```

**原理**：
- `cache='none'`：绕过宿主机页缓存，Guest 的 I/O 直接到达块设备，避免双重缓存
- `io='native'`：使用 Linux 原生异步 I/O（AIO），比 QEMU 线程池模式效率更高
- `type='raw'`：裸设备直接传递，无 qcow2 元数据开销

### 四、宿主机网络参数调优

#### 9. 内核网络缓冲区

```bash
# 增大 TCP/Socket 缓冲区
sudo sysctl -w net.core.rmem_max=16777216      # 16MB
sudo sysctl -w net.core.wmem_max=16777216      # 16MB
sudo sysctl -w net.core.rmem_default=1048576   # 1MB
sudo sysctl -w net.core.wmem_default=1048576   # 1MB

# TCP 自动调优范围
sudo sysctl -w net.ipv4.tcp_rmem="4096 1048576 16777216"
sudo sysctl -w net.ipv4.tcp_wmem="4096 1048576 16777216"

# 网络队列深度
sudo sysctl -w net.core.netdev_max_backlog=5000
sudo sysctl -w net.core.somaxconn=65535
```

持久化配置：
```bash
cat << EOF | sudo tee /etc/sysctl.d/99-net-perf.conf
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.core.rmem_default = 1048576
net.core.wmem_default = 1048576
net.core.netdev_max_backlog = 5000
net.core.somaxconn = 65535
net.ipv4.tcp_rmem = 4096 1048576 16777216
net.ipv4.tcp_wmem = 4096 1048576 16777216
EOF
sudo sysctl -p /etc/sysctl.d/99-net-perf.conf
```

**原理**：默认的内核网络缓冲区（通常 128KB-256KB）在高带宽场景下成为瓶颈。增大缓冲区允许 TCP 窗口自动扩展到更大值，充分利用高带宽链路。

#### 10. virbr0 MTU 调整

```bash
sudo ip link set virbr0 mtu 9000
```

**原理**：增大 MTU 到 9000（Jumbo Frame）减少了每 GB 数据需要处理的数据包数量约 6 倍（1500→9000），直接降低 CPU 中断处理和协议栈开销。

### 五、Guest OS 内部调优

#### 11. 启用多队列

```bash
sudo ethtool -L eth0 combined 8
```

**原理**：虽然 VM XML 定义了 8 个队列，但 Guest 内部需要通过 ethtool 激活才能生效。激活后网络中断会分散到多个 CPU 核心，实现真正的多核并行网络处理。

#### 12. Guest MTU 设置

```bash
sudo ip link set eth0 mtu 9000
```

**原理**：需要与宿主机 virbr0 的 MTU 匹配，否则大于 1500 字节的数据包会被分片，反而降低性能。

#### 13. Guest 内核网络参数

```bash
sudo sysctl -w net.core.rmem_max=16777216
sudo sysctl -w net.core.wmem_max=16777216
sudo sysctl -w net.core.rmem_default=1048576
sudo sysctl -w net.core.wmem_default=1048576
sudo sysctl -w net.core.netdev_max_backlog=5000
sudo sysctl -w net.core.somaxconn=65535
sudo sysctl -w net.ipv4.tcp_rmem="4096 1048576 16777216"
sudo sysctl -w net.ipv4.tcp_wmem="4096 1048576 16777216"
```

**原理**：Guest 内核有独立的网络参数空间，需要与宿主机同步调优，否则 Guest 侧的小缓冲区会成为瓶颈。

## 未优化项及原因

| 项目 | 未使用原因 |
|------|-----------|
| SR-IOV 网卡直通 | AWS c5n.metal 的 ENA 网卡不支持 KVM 内的 SR-IOV 直通 |
| macvtap 直通 | AWS ENA 驱动不支持 macvtap/macvlan 模式 |
| DPDK (Data Plane Development Kit) | 需要专用应用层支持，iperf3 不兼容 |
| AF_XDP | 需要应用层适配 |
| OVS-DPDK 桥接 | 架构过重，且需要应用层配合 |

## 多流性能未达 100% 的分析

优化后多流性能达到物理机的 58%（13.4 vs 23.1 Gbits/sec），未能达到 100% 的原因：

1. **NAT 开销**：所有 Guest 流量需经过 virbr0 NAT 转换，增加了每包处理的 CPU 指令数
2. **虚拟交换机开销**：virbr0 是 Linux bridge，每个包需要查表、转发、地址转换
3. **中断合并效率**：virtio-net 的中断合并策略不如物理 ENA 网卡的硬件中断合并高效
4. **vhost 线程调度**：vhost 工作线程仍需内核调度器管理，存在上下文切换开销
5. **QEMU 控制面**：虽然数据面由 vhost 处理，但 QEMU 仍参与部分控制面操作

要进一步缩小差距，需要使用 SR-IOV 直通或 DPDK 等绕过内核协议栈的技术，但这些在当前 AWS 环境中不可用。

## 完整优化清单（一键部署）

### 宿主机配置脚本

```bash
#!/bin/bash
# host-optimize.sh - KVM 宿主机网络性能优化

# 1. 加载内核模块
modprobe vhost_net
echo "vhost_net" > /etc/modules-load.d/vhost-net.conf

# 2. 禁用 bridge netfilter
modprobe br_netfilter
sysctl -w net.bridge.bridge-nf-call-iptables=0
sysctl -w net.bridge.bridge-nf-call-ip6tables=0
sysctl -w net.bridge.bridge-nf-call-arptables=0

# 3. 配置大页内存（根据 VM 内存调整，需 > VM RAM）
echo 8192 > /proc/sys/vm/nr_hugepages

# 4. 网络缓冲区调优
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216
sysctl -w net.core.rmem_default=1048576
sysctl -w net.core.wmem_default=1048576
sysctl -w net.core.netdev_max_backlog=5000
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_rmem="4096 1048576 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 1048576 16777216"

# 5. virbr0 MTU
ip link set virbr0 mtu 9000

echo "Host optimization complete."
```

### Guest 配置脚本

```bash
#!/bin/bash
# guest-optimize.sh - KVM Guest 网络性能优化
```

## 结论

通过 10 项调优措施，在不使用 SR-IOV/macvtap 硬件直通的前提下：

- **单流网络性能**：从 96.4% 提升到 **100%**，完全消除虚拟化开销
- **多流网络性能**：从 40.0% 提升到 **58.0%**，提升幅度 45%
- **磁盘 I/O 性能**：保持不变，无退化

其中影响最大的三项优化是：**vhost-net 内核模块**、**多队列 virtio-net** 和 **CPU 绑定**。这三项组合解决了 KVM 网络虚拟化的核心瓶颈——用户态/内核态切换、单队列瓶颈和 CPU 缓存失效。

多流性能未能达到 100% 的根本原因在于：在 virtio-net + NAT 桥接架构下，每个数据包仍需经过 Guest virtio 驱动 → vhost 内核线程 → virbr0 Linux bridge → iptables NAT 转换 → 物理 ENA 网卡这一完整软件路径，相比物理机直接通过 ENA 网卡发送多出了至少 3 层软件处理开销，而这些开销在多流并发时会随线程数线性放大。要彻底消除这一差距，唯一的办法是使用 SR-IOV 或 macvtap 将物理网卡直通给 Guest，绕过宿主机的整个网络协议栈，但 AWS ENA 网卡不支持这些直通模式，因此在当前环境下 58% 已接近 virtio-net NAT 架构的理论上限。
