# 在 RHEL 系统上利用 GPU 加速进行 vLLM 性能分析

## 引言

### 背景与动机
在大型语言模型（LLM）的应用中，理解其性能特征对于服务优化至关重要。对于刚接触 vLLM 和 LLM 基础设施的工程师来说，性能分析可能看起来是一项艰巨的任务。然而，借助火焰图（flame graphs）等可视化工具，我们能够直观地洞察程序的执行流程，精准定位性能瓶颈，从而为优化提供清晰的起点。

### 文档目标
本文旨在提供一份详尽的指南，指导用户如何在配备了 NVIDIA GPU 的 Red Hat Enterprise Linux (RHEL) 系统上，对 vLLM 推理服务器进行性能分析。我们将以 vLLM 官方的性能分析文档为主要参考，并根据我们的特定环境对步骤进行调整和阐述。

整个过程主要分为三个核心阶段：
1.  **环境搭建**：在 RHEL 服务器上配置必要的 NVIDIA 驱动程序和容器工具套件（Container Toolkit）。
2.  **基础性能分析（使用 PyTorch Profiler）**：运行 vLLM 内置的 PyTorch Profiler，捕获一次推理请求的完整执行轨迹（trace）。
3.  **高级性能分析（使用 NVIDIA Nsight Systems）**：构建一个包含 NVIDIA 高级分析工具的自定义容器镜像，以获取更深层次的 GPU 运行数据。

- **上游参考文档**: [vLLM Profiling Documentation](https://docs.vllm.ai/en/stable/contributing/profiling.html?h=profil)

## 第一部分：环境配置

在开始分析 vLLM 之前，我们必须首先准备好 RHEL 服务器环境，确保其能够支持 GPU 加速的容器化应用。

### 步骤 1.1：安装 NVIDIA 驱动程序

首先，我们需要安装 NVIDIA 驱动程序。这是操作系统与 GPU 硬件通信的基础，是发挥 GPU 计算能力的前提。

```bash
# 安装与当前内核版本匹配的开发包，这是构建驱动模块所必需的依赖。
# 更多信息请参考 NVIDIA 官方文档：
# https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/index.html#rhel-installation-network
dnf install -y kernel-devel-matched kernel-headers

# 启用 CodeReady Builder (CRB) 软件源，以获取额外的开发工具和库。
dnf config-manager --set-enabled crb

# 定义发行版和架构变量，以便后续拼接软件源 URL。
distro=rhel9
arch=x86_64

# 将 NVIDIA CUDA 软件源添加到系统的包管理器配置中。
dnf config-manager --add-repo https://developer.download.nvidia.com/compute/cuda/repos/$distro/$arch/cuda-$distro.repo

# 清理并刷新包管理器缓存，确保使用的是最新的软件源信息。
dnf clean expire-cache

# 启用基于 DKMS 的开源 NVIDIA 驱动模块。DKMS (Dynamic Kernel Module Support) 可以在内核更新后自动重新编译驱动模块。
dnf module enable -y nvidia-driver:open-dkms
# 作为替代方案，您也可以使用 `dnf module enable nvidia-driver:latest-dkms` 来安装最新的闭源驱动。

# 安装 NVIDIA 开源驱动包。
dnf install -y nvidia-open
# 若要卸载，可以运行 `dnf remove -y nvidia-open`。
# 如果选择安装闭源驱动，通常会使用 `dnf install cuda-drivers`。
```

### 步骤 1.2：安装 NVIDIA Container Toolkit

NVIDIA Container Toolkit 是一套关键组件，它允许容器（如 Podman 或 Docker）安全、高效地访问宿主机的 GPU 资源。我们将安装它来为 Podman 启用 GPU 支持。

```bash
# 添加 NVIDIA Container Toolkit 的软件源。
# 更多信息请参考官方安装指南：
# https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html
curl -s -L https://nvidia.github.io/libnvidia-container/stable/rpm/nvidia-container-toolkit.repo | \
  sudo tee /etc/yum.repos.d/nvidia-container-toolkit.repo

# 为了保证环境的稳定性，我们安装一个特定版本的工具套件组件。
export NVIDIA_CONTAINER_TOOLKIT_VERSION=1.17.8-1
sudo dnf install -y \
      nvidia-container-toolkit-${NVIDIA_CONTAINER_TOOLKIT_VERSION} \
      nvidia-container-toolkit-base-${NVIDIA_CONTAINER_TOOLKIT_VERSION} \
      libnvidia-container-tools-${NVIDIA_CONTAINER_TOOLKIT_VERSION} \
      libnvidia-container1-${NVIDIA_CONTAINER_TOOLKIT_VERSION}

# 生成 CDI (Container Device Interface) 规范文件。这个文件定义了容器运行时如何发现和使用 GPU 设备。
sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml

# 列出可用的 CDI 设备，以确认配置是否成功。
nvidia-ctk cdi list
# 预期的输出如下，表明系统已成功识别出可用的 GPU 设备：
# INFO[0000] Found 3 CDI devices
# nvidia.com/gpu=0
# nvidia.com/gpu=GPU-7e22d269-01f7-77c4-be2c-18969b4eec98
# nvidia.com/gpu=all
```

### 步骤 1.3：在容器中验证 GPU 访问

现在，让我们运行一个测试容器，以确保它能够成功访问和使用宿主机的 GPU。


## 第二部分：使用 PyTorch Profiler 进行基础性能分析

环境准备就绪后，我们现在可以运行 vLLM 服务器，并执行一次基础的性能分析。

### 步骤 2.1：初始推理测试

在深入分析之前，首先要确认 vLLM 推理服务器在当前环境中能否正常工作。这个基线测试步骤至关重要，它能确保后续遇到的任何问题都与性能分析本身相关，而不是基础设置的问题。

我们将启动 vLLM 容器，并发送一个简单的推理请求来验证其功能。关于 Red Hat AI Inference Server 的详细部署说明，请参考[官方文档](https://docs.redhat.com/en/documentation/red_hat_ai_inference_server/3.2/html-single/getting_started/index#inference-rhaiis-with-podman-nvidia-cuda_getting-started)。

```bash
# 创建一个目录用于存储容器数据，例如模型缓存。
mkdir -p rhaiis-cache
chmod g+rwX rhaiis-cache

# 创建一个环境文件来存储您的 Hugging Face 令牌。
echo "export HF_TOKEN=<your_HF_token>" > private.env
source private.env

# 运行 vLLM 容器，并配置必要的 GPU 和卷映射。
# --shm-size=8g: 分配 8GB 的共享内存（/dev/shm），这对于高性能计算中的进程间通信至关重要。
# --userns=keep-id:uid=1001: 确保容器内的用户映射到宿主机的特定用户，从而简化挂载卷的文件权限管理。
podman run --rm -it \
--device nvidia.com/gpu=all \
--security-opt=label=disable \
--shm-size=8g -p 8000:8000 \
--userns=keep-id:uid=1001 \
--env "HUGGING_FACE_HUB_TOKEN=$HF_TOKEN" \
--env "HF_HUB_OFFLINE=0" \
--env "VLLM_NO_USAGE_STATS=1" \
-v ./rhaiis-cache:/home/vllm:Z \
registry.redhat.io/rhaiis/vllm-cuda-rhel9:3.2.1 \
--model RedHatAI/Qwen3-8B-FP8-dynamic \
--tensor-parallel-size 1
```

服务器运行后，打开一个新的终端，发送一个测试推理请求。为了快速验证，我们将输出限制为 50 个 token。

```bash
# 在新终端中，向服务器发送一个测试请求。
# 我们将输出限制为 50 个 token 以进行初步测试。
curl -X POST -H "Content-Type: application/json" -d '{
"prompt": "What is the capital of France?",
"max_tokens": 50
}' http://127.0.0.1:8000/v1/completions | jq

# 成功的响应将确认服务器工作正常。
# {
#   "id": "cmpl-206df592b55f47faaa28e4183f6f9f55",
#   ...
#   "usage": {
#     "prompt_tokens": 7,
#     "total_tokens": 57,
#     "completion_tokens": 50
#   }
# }
```

### 步骤 2.2：在性能分析模式下运行

确认服务器正常工作后，我们可以重新启动它，并启用 PyTorch Profiler。vLLM 提供了一种便捷的方式，通过设置环境变量来激活分析器。

```bash
# 再次运行容器，但这次设置 VLLM_TORCH_PROFILER_DIR 环境变量。
# 这会指示 vLLM 将生成的性能轨迹文件保存到容器内的指定目录。
# 为了进行更精细的分析，vLLM 还支持其他分析器变量，用于捕获张量形状、内存使用、堆栈跟踪和 FLOPs。
# --env "VLLM_TORCH_PROFILER_RECORD_SHAPES=1"
# --env "VLLM_TORCH_PROFILER_WITH_PROFILE_MEMORY=1"
# --env "VLLM_TORCH_PROFILER_WITH_STACK=1"
# --env "VLLM_TORCH_PROFILER_WITH_FLOPS=1"
podman run --rm -it \
--device nvidia.com/gpu=all \
--security-opt=label=disable \
--shm-size=8g -p 8000:8000 \
--userns=keep-id:uid=1001 \
--env "HUGGING_FACE_HUB_TOKEN=$HF_TOKEN" \
--env "HF_HUB_OFFLINE=0" \
--env "VLLM_NO_USAGE_STATS=1" \
--env "VLLM_TORCH_PROFILER_DIR=/home/vllm" \
-v ./rhaiis-cache:/home/vllm:Z \
registry.redhat.io/rhaiis/vllm-cuda-rhel9:3.2.1 \
--model RedHatAI/Qwen3-8B-FP8-dynamic \
--tensor-parallel-size 1
```

在第二个终端中，我们首先发送一个命令来启动性能分析。
```bash
# 在终端 2 中，发送命令以启动性能分析。
curl -X POST http://localhost:8000/start_profile
```

接着，我们发送一个推理请求，并将 token 数量保持在较低的水平（10），以确保生成的轨迹文件易于分析。
```bash
# 发送一个推理请求。我们使用较少的 token 数量（10），
# 以便生成的轨迹文件更易于分析。

"prompt": "What is the capital of France?",
"max_tokens": 10
}' http://127.0.0.1:8000/v1/completions | jq
```

请求完成后，我们发送另一个命令来停止分析器。
```bash
# 发送命令以停止性能分析。
curl -X POST http://localhost:8000/stop_profile
```

此时，轨迹文件已经生成，并可以在我们挂载的缓存目录中找到。

### 步骤 2.3：分析性能轨迹

生成的 `.pt.trace.json.gz` 文件可以使用像 [Perfetto UI](https://ui.perfetto.dev/) 这样的轨迹查看器进行分析。

打开轨迹文件后，我们可以观察到几个清晰的模式：
1.  **Token 生成峰值**：在顶层视图中，我们可以看到 10 个明显的峰值，这与我们请求的 `max_tokens: 10` 完全对应。每个峰值代表生成一个 token 的过程。
    <img src="imgs/2025.09.vllm.gpu.profile.md/2025-09-18-22-35-07.png" width="1024">

2.  **模型层执行**：放大单个 token 生成的峰值，会发现它由 36 个更小的、顺序执行的峰值组成。这对应于 Qwen3-8B 模型中的 36 个解码器层（decoder layers）。
    <img src="imgs/2025.09.vllm.gpu.profile.md/2025-09-18-22-33-49.png" width="1024">

3.  **CUDA Kernel 执行**：通过进一步放大轨迹并选择一个 `cudaGraphLaunch` 事件，我们可以检查底层的 GPU 操作。这揭示了多个 CUDA 内核（kernels）的调用，它们负责实际的计算任务。其中包括用于通用矩阵乘法（GEMM）的高度优化的 `cutlass::gemm` 内核，这是 Transformer 模型中的基本运算。
    <img src="imgs/2025.09.vllm.gpu.profile.md/2025-09-18-22-16-27.png" width="1024">

为了理解代码路径，我们可以检查 vLLM 的源代码。轨迹显示了对 `qwen3` 的 `forward` 函数的调用。查看源代码发现，`Qwen3Model` 直接继承自 `Qwen2Model`。

- **源码**: [`vllm/model_executor/models/qwen3.py`](https://github.com/vllm-project/vllm/blob/bf1d46913ba8cc772213472a90ad042970138741/vllm/model_executor/models/qwen3.py#L256)
```python
class Qwen3Model(Qwen2Model):
    ...
```

`Qwen2Model` 中的 `forward` 方法会遍历模型的各个层，这些层是 `Qwen2DecoderLayer` 的实例。

- **源码**: [`vllm/model_executor/models/qwen2.py`](https://github.com/vllm-project/vllm/blob/bf1d46913ba8cc772213472a90ad042970138741/vllm/model_executor/models/qwen2.py#L365)
```python
# ...
        for idx, layer in enumerate(
                islice(self.layers, self.start_layer, self.end_layer)):
            # ...
            hidden_states, residual = layer(positions, hidden_states, residual)
# ...
```

最后，`Qwen2DecoderLayer` 的 `forward` 方法揭示了 Transformer 模块的标准组件：层归一化（layer normalization）、自注意力机制（self-attention）和多层感知机（MLP）。

- **源码**: [`vllm/model_executor/models/qwen2.py`](https://github.com/vllm-project/vllm/blob/bf1d46913ba8cc772213472a90ad042970138741/vllm/model_executor/models/qwen2.py#L245)
```python
# ...
    def forward(
        self,
        positions: torch.Tensor,
        hidden_states: torch.Tensor,
        residual: Optional[torch.Tensor],
    ) -> tuple[torch.Tensor, torch.Tensor]:
        # Self Attention
        if residual is None:
            residual = hidden_states
            hidden_states = self.input_layernorm(hidden_states)
        else:
            hidden_states, residual = self.input_layernorm(
                hidden_states, residual)
        hidden_states = self.self_attn(
            positions=positions,
            hidden_states=hidden_states,
        )

        # Fully Connected
        hidden_states, residual = self.post_attention_layernorm(
            hidden_states, residual)
        hidden_states = self.mlp(hidden_states)
        return hidden_states, residual
# ...
```

这一系列的分析证实了火焰图准确地反映了模型的架构和执行流程。

## 第三部分：使用 NVIDIA Nsight Systems 进行高级性能分析

为了获得更详细的、硬件级别的视图，我们可以使用 NVIDIA Nsight Systems。这需要我们构建一个包含 Nsight CLI 工具的自定义容器镜像。

### 步骤 3.1：构建支持 Nsight 的容器

创建一个 `Dockerfile` 来构建新的镜像。

```dockerfile
# nsys.dockerfile
FROM registry.redhat.io/rhaiis/vllm-cuda-rhel9:3.2.1

USER root

# 添加 NVIDIA 开发者软件源以安装 Nsight Systems
RUN rpm --import https://developer.download.nvidia.com/compute/cuda/repos/ubuntu1804/x86_64/7fa2af80.pub
RUN microdnf install -y dnf && microdnf clean all
RUN microdnf install -y dnf-plugins-core && microdnf clean all
RUN dnf config-manager --add-repo "https://developer.download.nvidia.com/devtools/repos/rhel$(source /etc/os-release; echo ${VERSION_ID%%.*})/$(rpm --eval '%{_arch}' | sed s/aarch/arm/)/"

# 安装 Nsight Systems CLI
RUN dnf install -y nsight-systems-cli

USER 2000

# 设置容器的入口点，使其自动使用 nsys profile 来包装 vLLM 服务器的启动命令。
# --trace-fork-before-exec=true: 确保 nsys 能够跟踪由主进程 fork 出的子进程。
# --cuda-graph-trace=node: 提供对 CUDA Graph 节点的详细跟踪。
ENTRYPOINT ["nsys", "profile", "-o", "/home/vllm/report.nsys-rep", "--trace-fork-before-exec=true", "--cuda-graph-trace=node", "python3", "-m", "vllm.entrypoints.openai.api_server"]
```

构建并推送镜像：

```bash
podman build -t quay.io/wangzheng422/qimgs:vllm-cuda-rhel9-3.2.1-nsys-2025.09.17-v01 -f nsys.dockerfile .
podman push quay.io/wangzheng422/qimgs:vllm-cuda-rhel9-3.2.1-nsys-2025.09.17-v01
```

### 步骤 3.2：捕获 Nsight Systems 轨迹

有了自定义容器镜像后，我们就可以执行一次性能分析运行。由于容器被配置为在启动时自动通过 `nsys` 分析器来运行 vLLM 服务器，因此分析过程在容器启动时就已开始。

首先，启动自定义容器。这将以性能分析模式启动 vLLM 服务器。

```bash
# 启动自定义容器。ENTRYPOINT 已被配置为使用 `nsys profile` 包装 vLLM 服务器命令，
# 因此性能分析会自动开始。
podman run --rm -it \
--device nvidia.com/gpu=all \
--security-opt=label=disable \
--shm-size=8g -p 8000:8000 \
--userns=keep-id:uid=1001 \
--env "HUGGING_FACE_HUB_TOKEN=$HF_TOKEN" \
--env "HF_HUB_OFFLINE=0" \
--env "VLLM_NO_USAGE_STATS=1" \
-v ./rhaiis-cache:/home/vllm:Z \
quay.io/wangzheng422/qimgs:vllm-cuda-rhel9-3.2.1-nsys-2025.09.17-v01 \
--model RedHatAI/Qwen3-8B-FP8-dynamic \
--tensor-parallel-size 1
```

在服务器运行时，打开一个新终端并发送一个推理请求。这个操作会触发我们想要分析的特定代码路径。

```bash
# 在新终端中，发送一个推理请求以触发被分析的代码路径。
# 这确保了 Nsight 轨迹能够捕获模型执行期间的 GPU 活动。
curl -X POST -H "Content-Type: application/json" -d '{
"prompt": "What is the capital of France?",
"max_tokens": 10
}' http://127.0.0.1:8000/v1/completions | jq
```

推理请求完成后，您可以在第一个终端中按 `Ctrl+C` 来停止容器。终止时，Nsight Systems 会处理收集到的数据，并将最终的轨迹文件保存到容器内的指定路径。

```bash

```

### 步骤 3.3：分析 Nsight 报告

将 `report.nsys-rep` 文件从 `rhaiis-cache` 目录复制到您的本地机器，并使用 NVIDIA Nsight Systems GUI 打开它。该工具提供了 CPU 和 GPU 活动的详细时间线，包括 CUDA 内核启动、内存传输和 API 调用，从而可以进行深入的性能分析。
